## 1. 为什么设计这条用例

单测能证明「每个函数是对的」，但不能证明「这几条链路串起来还是对的」。
这条用例专挑三个最容易在集成处断掉的地方：

1. **确认前不落库** —— 如果确认卡和出单的顺序写反了，单测看不出来，用户会看到两张工单
2. **两个客服先后改同一张单** —— 乐观锁只有一个人测不出来，必须两个会话
3. **回执幂等** —— 只轮询一次看不出重复，必须连问三次

## 5. 这条用例顺带证明的三件事

1. **确认卡拿到的不是字段表，而是一句话**
   `CONFIRM` 响应里只有 `summary` + `missing: ['订单号','原因']`，
   没有 `values`、没有 `level`。顾客看不到内部的分级体系。

2. **摘要缺失也不会给空白确认卡**
   模型这次没给 summary，后端用已抽到的字段兜底拼了一句。
   （默认路径的回归测试在 `ConversationOrchestratorTest.confirmSummaryFallsBackToFields`）

3. **`assignee` 自动认领 + `lastActor` 审计**
   张三第一次保存时自动认领；李四后来改动，`assignee` 仍是张三，
   但 `lastActor` 变成李四——「谁负责」和「谁最后动过」是两件事。

## 6. 未覆盖的部分（明确说明，避免误以为已验）

| 未覆盖 | 原因 | 怎么补 |
|---|---|---|
| 页面 UI 的视觉与交互 | 本用例走接口层 | 手动清单（见下） |
| 顾客端 4 秒轮询的真实体感 | 脚本只能模拟轮询调用 | 打开两个浏览器窗口：顾客 + 人工端 |
| 推送 | 设计上就是轮询，没有推送 | 见 README「已知缺口」 |
| 并发真的同时点保存 | 脚本是串行，靠"旧版本"模拟 | 需要并行压测，两周项目未做 |

### 手动 UI 清单（配合本用例）

1. 顾客端发那三句话 → 出现黄色确认卡，摘要可编辑，显示「还缺少：订单号 原因」
2. 改一句摘要 → 点「确认并提交给人工」→ 绿色卡片显示工单号
3. 人工端登录 `zhangsan/123456` → 列表看到新工单（红色「待核实」+「顾客已确认」标记）
4. 打开详情 → 保存 → 顾客端 **4 秒内**出现「已由人工客服受理」气泡
5. 另开一个浏览器窗口登录 `lisi` → 打开同一张单 → 用旧内容保存 → 应提示「刚被他人改过，已刷新」
