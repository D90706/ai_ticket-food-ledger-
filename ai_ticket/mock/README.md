mock/ · 前后端共享的契约文件
================================================================

用途：这两人同时开工时，唯一必须事先对齐的东西。
     前端按这五份文件的结构开发界面，不必等后端接口写完。
     后端改字段名 = 破坏契约，必须同步改本目录并通知对方。

规则：
    1. 这五份是契约，不是示例数据。字段名、层级、枚举取值
       必须与应用实际行为一致。
    2. 后端的 DTO / 实体字段名一律以本目录为准。
    3. 修改任何一份，都要在提交信息里写「contract: ...」。


----------------------------------------------------------------
【文件清单】
----------------------------------------------------------------

  template.json          电商售后工单（主模板，version 3）
  template-it.json       IT 设备报修工单（验证通用性的第二模板）
  extraction-result.json 抽取层的输出契约（四字段）
  ticket.json            两张已生成工单：一张黄、一张红
  preview-response.json  试抽接口的完整响应


----------------------------------------------------------------
【三处容易搞错的地方】
----------------------------------------------------------------

1. role 还是 role_text
   数据库列名是 role_text（避开关键字），
   API / JSON 里一律叫 role。
   契约以 JSON 为准，实体上写 @TableField("role_text")。

2. values 还是 valuesData
   抽取层的输出叫 values；
   工单表把它落库到 values_data 列，实体属性叫 valuesData。
   三个名字对应三个层次，不要混。

3. basis 必须是对话原文的子串
   这是「忠实性」校验的唯一手段（dialogue.contains(basis)）。
   所以 mock 里的 basis 都能在 dialogue 里原样找到，
   改名、缩写、润色都会让校验失败。
   preview-response.json 特意保留了 dialogue 字段，就是给这个用的。

3. decisionOptions 还是 decision_options
   数据库列名是 decision_options，但 API 的请求体与响应体
   一律用 camelCase：decisionOptions。

   这条是实测踩出来的：两处 mock 模板最初写成了 decision_options，
   提交时被后端当作「决策项为空」直接返回 400。
   前端调接口同理——请求体必须是 camelCase。


----------------------------------------------------------------
【数值是怎么算出来的】
----------------------------------------------------------------

ticket.json 的两张工单可以手算复核，这是它们存在的意义。

▍工单 101（黄）

    必填 order_id / reason 都有值        → 无阻断缺陷
    选填 evidence 为空                   → 降级缺陷
    basis 四项齐全且都是原文子串          → 忠实性通过
    → level = YELLOW

    fillRate         = 4 / 5   = 0.8
    requiredRate     = 2 / 2   = 1.0
    optionalCoverage = 2 / 3   = 0.667
    basisCoverage    = 4 / 4   = 1.0

    suggestion 被采用（因为 missingRequired 为空）

▍工单 102（红）

    必填 order_id / reason 都为空        → 两条阻断缺陷
    → level = RED，后面两个维度不再参与定级

    fillRate / requiredRate / optionalCoverage / basisCoverage 全为 0.0

    suggestion = null
      ← 关键：即使模型给出了建议，代码必须强制置空（缺失必填时不许建议）

    status = INFO_INCOMPLETE
      ← 追问次数达到上限后强制出单，这是必填项问不出来时的唯一出口

    needsClarify = true
      ← 这条工单之所以存在，就是因为它信息不全

    degrading = 3 条
      ← 三个选填字段全缺，每个字段一条

    messages = 3 条，但来源不同：
      前两条由核验层产出（缺 2 项必填 / 缺 3 项选填），
      最后一条「追问已达上限，按「信息不全」出单，需人工补齐」
      由编排层追加 —— 核验层不知道追问了几次，也不该知道。

▍一个约定：分母为 0 的情况

    102 号工单没有任何非空字段，basisCoverage 严格说无意义。
    统一约定为 0.0，而不是 null，避免前端到处判空。
    前端展示时可以说「无依据可校验」而不是显示 0%。


----------------------------------------------------------------
【契约锚点：改这三处代价最高】
----------------------------------------------------------------

    1. fields 元素的结构
       key / label / type / required / options / pattern

    2. 抽取结果的四个字段名
       values / basis / suggestion / summary

    3. quality 的 level 取值
       RED / YELLOW / GREEN（大写，不要用红黄绿或 green）

这三处一动，前后端都要改，数据库也要迁移。
其它字段（比如 messages 的文案）可以自由调整。
