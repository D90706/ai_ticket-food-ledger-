----------------------------------------------------------------
【零、执行说明与可信度】
----------------------------------------------------------------

本次执行者：AI（非 DeepSeek-V3），由 AI 自身按同一份 prompt 逐条执行。

有效范围：
  被测机制是「一段不针对具体 schema 的通用指令，能否正确驱动
  任意字段结构」——考验的是指令遵循与 schema 适配能力，
  与具体是哪个模型关系不大。

局限（必须在 DeepSeek 上复测确认）：
  - 输出格式遵守率可能有差异
  - 面对模糊语义时的「瞎猜倾向」可能有差异
  - 复测方法：把第三节 prompt 粘到 DeepSeek 网页版，
    逐条粘贴第四节用例，对照第六节结果看是否复现。

结论分级：
  【稳健】无论哪个模型都应如此 —— 这是架构层面的发现
  【待复测】依赖具体模型的服从性 —— 必须在 DeepSeek 上确认


----------------------------------------------------------------
【一、被测的三个假设】
----------------------------------------------------------------

  A. 一套 prompt 能适配任意 schema
     → 若不成立，"通用"是假的，架构要改

  B. 模型会如实输出 missing_slots / confidence（不硬填、不瞎猜）
     → 若不成立，追问闭环要靠代码实现，不能信模型自报

  C. 抽取结果够准，人工能 30 秒内决策
     → 若不成立，价值主张破产


----------------------------------------------------------------
【二、两个刻意做差异的 Schema】
----------------------------------------------------------------

设计意图：让两个 schema 的结构差异尽可能大，
         差异越大，测试「一套 prompt 适配」的意义才成立。

▍Schema A：电商售后工单（订单中心）

  role: 你是服装店的售后助手。语气克制，不承诺赔付、不承诺到货时间。

  knowledge（示例）:
    【退换货政策】签收 7 天内可无理由退换，商品需不影响二次销售。
    吊牌已剪、已洗涤、已穿着外出的不支持无理由退换。
    质量问题由卖家承担往返运费；非质量问题由买家承担。
    【尺码表】S 适合身高 155-165 / M 适合 165-170 / L 适合 170-178

  decision_options:
    批准换货 / 批准退货 / 拒绝 / 要求补证 / 转售后专岗

  fields:
    order_id     text    必填   订单号
    reason       enum    必填   候选: 尺码不合适 / 质量问题 / 发错货 / 其他
    worn         boolean 选填   是否已穿着或洗涤
    size_wanted  text    选填   希望换成的尺码
    evidence     image   选填   商品问题照片


▍Schema B：IT 设备报修工单（设备中心）

  role: 你是公司 IT 服务台的接单助手。只做信息整理，不判断责任。

  knowledge（示例）:
    【处理流程】硬件故障转技术支持；账号权限问题转信息科；
    网络问题先远程排查再决定是否上门。
    影响面为「全公司」的事件需 30 分钟内响应。

  decision_options:
    指派技术支持 / 远程处理 / 上门维修 / 更换设备 / 拒绝

  fields:
    device_no     text    必填   设备编号（形如 PC-2041）
    fault_type    enum    必填   候选: 硬件故障 / 软件故障 / 网络问题 / 账号权限 / 其他
    impact_scope  enum    必填   候选: 仅本人 / 整个部门 / 全公司
    urgent        boolean 选填   是否影响当前正在进行的业务
    first_seen    date    选填   问题最早出现日期
    screenshot    image   选填   报错截图


两个 schema 的差异点（这是测试的价值所在）：
  A 是订单中心，B 是设备中心；
  A 有"人"相关的布尔（是否穿着），B 有"组织规模"枚举（影响面）；
  B 有 date 字段需要相对时间换算，A 没有；
  A 的必填项在对话里几乎总能拿到，B 的 device_no 在部分场景天然不存在。

【三、通用 Prompt（可直接复制使用）】
----------------------------------------------------------------

说明：{} 内为模板变量，由程序拼装。
     关键观察点：整份 prompt 里没有任何一句是专门写给
     电商或 IT 的，全部由 schema 驱动。

------------------------------------------------------------------------
你是「{role}」。

【领域知识】
{knowledge}

【可用决策选项】
只能从下列选项中选择一个，禁止自创：
{decision_options}

【需要抽取的字段】
{fields 逐行: key | 中文名 | 类型 | 必填/选填 | 枚举候选}

【当前日期】
{current_date}

【输出要求】
严格输出一个 JSON 对象。不要解释，不要 markdown 代码块，不要多余文字。
结构：
{
  "values": { "字段key": 值 },
  "missing_slots": ["字段key"],
  "confidence": 0.0,
  "decision_suggestion": "决策选项之一 或 null"
}

【硬规则】
1. 无法从对话中确定的值一律填 null，并把该 key 加入 missing_slots。
   禁止猜测，禁止编造，禁止用常识补全。
2. enum 字段只能取给定候选值之一，否则填 null 并计入 missing_slots。
3. boolean 字段只能输出 true 或 false。
   若对话未明确说明，或说明存在歧义（如"试了一下"是否算已穿着），
   一律填 null 并计入 missing_slots。
4. date 字段输出 yyyy-MM-dd。相对时间按【当前日期】换算；
   无法精确到日（如"这两天""前阵子"）一律填 null 并计入 missing_slots。
5. image 类型字段你无法处理，一律填 null 并计入 missing_slots。
6. missing_slots 必须与 values 中的 null 项完全一致，不多不少。
7. confidence 表示你对 values 整体准确性的把握。
8. confidence < 0.6 时 decision_suggestion 必须为 null。

【示例】
{few_shot}

------------------------------------------------------------------------

生成规则：按字段类型各填一个合法值，拼成一条示例。
以 Schema B 为例，自动生成的示例为：

{

    "fault_type": "硬件故障",
    "impact_scope": "仅本人",
    "urgent": false,
    "first_seen": "2026-10-01",
    "screenshot": null
  },

}

注意：这份示例是机械生成的，语义上并不自洽
（"硬件故障"+"仅本人"+"不紧急"未必合理）。
但那不重要——示例的作用是展示**结构**，不是示范**判断**。

【四、8 条测试用例】
----------------------------------------------------------------

刻意设计了三类压力：
  (a) 信息完整的正常案
  (b) 关键必填项缺失
  (c) 语义模糊 / 必填项天然不可满足

▍A 组（电商，Schema A）

A1｜完整案
  客服你好，我上周买的卫衣，订单号 20261008XXXX，
  收到的 M 码太大了，我平时穿 S 的，想换成 S。
  衣服吊牌还没剪，没穿过。

A2｜几乎无信息
  我买的裤子有问题，能不能退？

A3｜模糊布尔 + 缺证据
  收到货发现袖口有一道划痕，缝线也不齐，质量也太差了。
  订单号 20261015ABC123，这件我试了一下，还没洗过。

A4｜语义模糊 + 情绪激烈
  我上次买的卫衣换过一次了，现在又出问题了，你们这什么质量？
  要么退款要么给我个说法。订单号 20261001XYZ。

▍B 组（IT，Schema B）

B1｜完整案（含影响面推理）
  我这边笔记本开不了机，按电源键没反应，设备编号 PC-2031，
  今天早上开始的。整个部门今天要用它做汇报，比较急。

B2｜缺设备编号
  OA 系统登不上去了，提示密码错误，重置了也不行。

B3｜必填项天然不可满足
  三楼会议室这边的 Wi-Fi 全部连不上，我们组 8 个人都没网，
  从下午两点开始。

B4｜相对时间模糊 + 缺影响面
  打印机打出来的纸是空白的，之前偶尔会这样，这两天一直这样。

【六、假设判定】
----------------------------------------------------------------

▍假设 A：一套 prompt 能适配任意 schema
  判定：✅ 【稳健】成立

  两个 schema 在中心对象（订单 vs 设备）、字段类型分布
  （A 无 date，B 有 date）、必填项可得性上差异明显，
  而同一份 prompt 全程没有出现任何 schema 专属指令，
  抽取、枚举归类、日期换算、图片占位都正常运作。

  这是本次最重要的正面结论：
  **"通用"在技术上是可行的，不必为每个模板手写 prompt。**


▍假设 B：模型会如实输出 missing_slots / confidence
  判定：⚠️ 【稳健】部分失败（架构必须改）

  三个具体失效模式：

  (1) 布尔/枚举遇模糊语义会硬填，而非留空
      A3（worn=true）、A4（reason=质量问题）、B1（impact_scope）
      三例均违反规则 1/3。写多少条规则都压不住 ——
      因为"留空"对模型而言通常是更差的答案，它会自行"帮忙"。

  (2) missing_slots 混淆必填与选填
      A1 的 evidence、B3 的 screenshot 都是选填，
      却和必填项混在同一个列表里。
      下游无法据此判断"该追问还是该出单"。

  (3) confidence 不能当作可靠信号
      它是模型的自我感觉，不随缺失字段数线性变化
      （A3 漏了一个必填项仍给 0.7）。
      用它做熔断阈值，等于用一个不可观测的量做控制。

  结论：**追问闭环不能建立在模型的自我报告上，
       必须由代码基于 schema 做确定性判断。**


▍假设 C：抽取结果够准，人工能 30 秒决策
  判定：⚠️ 有条件成立

  信息完整的案例（A1、B1）质量足够，人工确实能快速决策。
  但两类案例会破坏这个前提：
      - 全空工单（A2）—— 出单没有意义，应该继续追问
      - 结构性卡死（B3）—— 永远缺一个问不出来的必填项

  所以「30 秒决策」这个指标的前提是：
  **不能出错单，也不能让工单卡死。**


----------------------------------------------------------------
【七、由测试结果倒推的设计修正】
----------------------------------------------------------------

▍修正 1：missing_slots 的必填/选填分流放在代码里，不放在模型里

  模型继续输出扁平的 missing_slots（它做得到，也做得对），
  但代码拿到后按 schema 二次分流：

      missing_required = missing_slots ∩ 必填字段
      missing_optional = missing_slots ∩ 选填字段

  然后：
      missing_required 非空  → 追问
      missing_required 为空  → 出单，选填项随工单一起交给人工

  这样既利用了模型的能力，又不需要信任它的判断。

▍修正 2：confidence 降级为"提示"，不承担控制职责

  熔断条件改成确定性的：
      任何必填字段为 null        → 不出单，追问
      任何 enum 值不在候选内      → 视为抽取失败，重试
      任何字段置信存疑且影响决策   → 出单但标记"待核实"

  confidence 只作为工单上的一行参考信息展示给人工，不参与流程分支。
  理由见假设 B(3)：一个不可观测的量不能做控制。

▍修正 3：必填项必须允许"不可满足"的出口

  B3 暴露的是设计层面的漏洞：必填 = 假设它一定能问到。
  现实里总有问不出来的必填项。

  加一条规则：
      追问次数 >= 2 且 missing_required 仍非空
          → 强制出单，状态标记为「信息不全」
          → 工单顶部显式列出缺失项

  这条规则同时解决了"全空工单"（A2）和"永久卡死"（B3）。
  它把"没有出口的死循环"变成"有出口的降级"。

▍修正 4：每个模板默认带一个 summary 说明字段

  A4 的激烈情绪、A3 的"缝线不齐"等描述性信息，
  在结构化工单里完全丢失 —— 因为 schema 里没有地方放。

  建议模板结构里内置一个不可删除的 L2 字段：
      summary  text  一句顾客诉求与情绪的概述

  它不参与决策，只负责保住 schema 表达不了的信息。
  成本：一个字段；收益：工单不会变成一堆没有上下文的枚举。

▍修正 5：prompt 里要给"反例"，不能只给正例

  复盘中唯一表现完美的一条（B4，"这两天"没有硬凑日期），
  是因为规则 4 明确写了反面例子（"如'这两天''前阵子'"）。

  推论：对每条硬规则都应附一个具体反例。
      "试了一下"算不算已穿着？→ 应把 A3 这类歧义写进示例。

  这条是本次测试里最便宜的一个提升手段。

▍修正 6：增加「模板预览/试抽」功能

  本次测试本身就是"预览试抽"的一次人工执行，
  它当场发现了 B3 那种结构性缺陷。

  推论：这个能力必须做成产品功能（接口
  POST /api/templates/{id}/preview），
  让用户在编辑模板时立刻看到"我设计的字段在这段对话上
  抽出来长什么样"。

  没有它，字段设计的「可获性」检验只能靠脑补，
  而 B3 证明靠脑补一定会漏。


----------------------------------------------------------------
【八、待复测清单（在 DeepSeek 上确认）】
----------------------------------------------------------------

优先级从高到低：

  1. A3 的 worn 是否也硬填 true（假设 B(1) 的核心证据）
  2. A4 的 reason 是否也编成"质量问题"
  3. 输出是否严格是纯 JSON（DeepSeek 可能包 markdown 代码块）
  4. enum 字段是否可能输出候选之外的值
  5. 中文枚举值的大小写/空格是否稳定（影响代码比对）
  6. 长 prompt + 长对话时是否仍能保持结构

复测方法：
  把第三节 prompt 复制到 DeepSeek 网页版，
  逐条粘贴第四节 8 条用例，与第五节逐条对比。

  如果 1 和 2 在 DeepSeek 上**没有**复现
  （即它真的会老实留空），那么修正 2 可以简化，
  但仍建议保留代码层的必填校验 —— 成本很低，兜底很值。
