================================================================
AI 客服工单引擎
================================================================

本目录只包含「AI 客服工单系统」一个工程（后端 8080 / 前端 5173 / 库 ai_ticket）。

    另一个独立工程「食材采购台账系统」已移到同级目录 ../food-ledger/：
       cd ../food-ledger && mvn spring-boot:run      # 后端 8081
       cd ../food-ledger/web && npm run dev          # 前端 5174
    它的数据库是 food_ledger，与这里的 ai_ticket 互不影响、无代码依赖。

把非结构化对话，压缩成结构化、可决策、可分级的工单。

    领域用户自定义字段与决策项
    AI 只负责「抽取」
    代码负责「够不够」
    人工负责「怎么处理」

技术栈：Spring Boot 3.4.8 + MySQL 8 + MyBatis-Plus 3.5.7
        Vue 3 + Vite + Element Plus
        DeepSeek（OpenAI 兼容协议，裸调 HTTP）


----------------------------------------------------------------
【一、这是什么，不是什么】
----------------------------------------------------------------

是：
    一个「对话 → 结构化数据」的抽取引擎 + 一套工单系统。
    schema 是数据不是代码，换业务只改配置不改代码。
    质量由代码对字段表做确定性核验，不给 AI 打分的权力。

不是：
    ✗ 聊天机器人。AI 不负责回答问题，只负责整理。
    ✗ 低代码平台。不做拖拽表单设计器、不做流程编排。
    ✗ 通用助手。只做一件事：把对话压成一张能决策的工单。

三个刻意的边界，写在 design 文档里，也在代码里：
    「不做」和「做」一样重要，因为每一项「顺便支持」
    都会稀释核心。


----------------------------------------------------------------
【二、四层架构】
----------------------------------------------------------------

    一、模板层   领域配置包
        role / knowledge / decision_options / fields（含必填与选填）
            │
            │  模板驱动 prompt
            ▼
    二、抽取层   只负责「看到什么」
        动态 Prompt → LLM → values / basis / suggestion / summary
        ★ 不输出置信度，不输出缺失清单
            │
            │  values + basis
            ▼
    三、核验层   只负责「够不够」——纯代码，无模型，可单测
        完备性 → 可决策性 / 忠实性 / 自洽性 → 分级
            │
            │  工单 + schema 快照 + 分级
            ▼
    四、工单层   人工决策
        分级提醒 / 状态机 / 指派 / 决策记录

最重要的一处分界在第二、三层之间：

    模型只回答「这段对话里看到了什么」，
    代码只回答「这些够不够用」。

为什么必须这样切：实测证明模型的自评不可靠。
缺 1 个必填项时它给 confidence 0.75，还自信地给出了处理建议。

【三、快速开始】
----------------------------------------------------------------

前置：JDK 21+（本项目在 23 上验证）、Maven 3.9+、MySQL 8、Node 18+

▍1 建库

    mysql -u root -p < src/main/resources/db/schema.sql

    会创建 ai_ticket 库、4 张表，并插入 2 个模板
    （电商售后工单 v3、IT 设备报修工单 v1）。

▍2 配置

    数据库口令和模型 key 都**不进仓库**，启动前用环境变量提供：

        set DB_PASSWORD=你的MySQL口令              # Windows
        set DEEPSEEK_API_KEY=sk-xxxx
        export DB_PASSWORD=你的MySQL口令            # bash
        export DEEPSEEK_API_KEY=sk-xxxx

    application.yml 里只有两个占位符：

        password: ${DB_PASSWORD:}
        api-key: ${DEEPSEEK_API_KEY:}

    两者留空的后果不同：

        口令空 → 启动时连不上库（这是预期的，别把真实口令写回仓库）
        key 空 → 能正常启动，只有调用模型时报「未配置 app.llm.api-key」，
                 模板管理、工单列表、核验层都不受影响。

▍3 后端

    mvn spring-boot:run

    http://localhost:8080/api/templates  应返回模板列表
    http://localhost:8080/swagger-ui.html  可看接口文档

▍4 前端

    cd web
    npm install     # 只需一次
    npm run dev

    用户端   http://localhost:5173/
    人工端   http://localhost:5173/agent/

    人工端需要登录（顾客端不需要）：
        演示账号  zhangsan / lisi
        初始密码  123456
    账号在首次启动时自动创建（AgentSeeder），密码只存 BCrypt 哈希。

    两个端是分开的：顾客只能对话，看不到工单与字段定义；
    人工端才有工单列表、批阅、模板配置。

    用 npm 而不是 pnpm：npm 随 Node.js 一起装，一定有。
    本仓库依赖是用 pnpm 装的，但 npm run 同样能跑——
    它只是读 package.json 的 scripts 去执行 node_modules/.bin/vite。

    想用 pnpm 的话（可选）：
        corepack enable pnpm     # Node 16+ 自带 corepack，无需全局安装
        pnpm -v

    ⚠ pnpm 11 会拦截依赖的安装脚本并在每次 run 前做依赖校验，
      项目已用 web/pnpm-workspace.yaml 关掉这两道门。
      若仍报 ERR_PNPM_IGNORED_BUILDS，见 web/README.md 的三种解法。

【五、接口一览】
----------------------------------------------------------------

    登录（人工端专用）
    POST   /api/auth/login                用户名 + 密码 → 写 session cookie
    GET    /api/auth/me                   我是谁（未登录返回 401）
    POST   /api/auth/logout               退出登录

    模板
    GET    /api/templates                 列表
    POST   /api/templates                 新建
    GET    /api/templates/{id}            详情
    PUT    /api/templates/{id}            整体提交，version + 1
    POST   /api/templates/{id}/preview    试抽，不落库  ★

    对话（用户端只用这三个）
    GET    /api/chat/templates            能咨询哪几类问题（只返回 id + 名称）
    POST   /api/chat/sessions             开新会话
    POST   /api/chat/sessions/{id}/messages  一轮对话 → ASK / CONFIRM / TICKET
    POST   /api/chat/sessions/{id}/confirm   顾客确认后才入队（仅信息不全的工单）
    GET    /api/chat/sessions/{id}/status    工单状态回执（顾客出单后轮询）
    GET    /api/chat/sessions/{id}/messages  历史消息

    工单
    GET    /api/tickets?status=&level=    列表
    GET    /api/tickets/{id}              详情（含 schema 快照与依据）
    PATCH  /api/tickets/{id}              状态 / 指派 / 决策 / 回问埋点

统一响应：{ code, message, data }，code === 0 表示成功。

▍试抽为什么单独标星

    字段设计是这套系统里唯一需要业务知识的环节，
    而「我设计的字段在这段对话上抽出来什么样」没法靠脑补。
    有了试抽，字段设计从盲猜变成可试错。
    它同时是最省事的调试工具：一条命令就能看出
    prompt 拼装、模型调用、结构校验、三维核验四条链路是否都活着。

【七、这个系统承诺什么，不承诺什么】
----------------------------------------------------------------

它承诺：
    信息齐不齐，能算准。
    依据在不在原文里，能查出来。
    缺什么，能说清楚。
    该不该追问、该不该出单，有确定的规则。

打回补全：人工处理不了的时候

    人工发现信息不够，可以把工单**打回**（status → RETURNED）。
    会话随即重开，顾客能继续说话；顾客补齐后，AI 重新抽取并
    **原地把同一张工单重新提交**（revision + 1，状态回到 PENDING）。

    为什么不新建一张单：
        顾客只该认一个单号。可追溯性不靠"不可变"来保证，
        而靠 revision 递增 + last_actor + 乐观锁。

    三条约束：
        最多打回 2 次 —— 防止「人工踢给顾客、顾客又补不出来」的死循环
        只能从 已指派 / 处理中 / 信息不全 / 待处理 打回
        打回后不能直接标记为已解决 —— 信息不全的单子不该被"结单"了事

    人工可以留一句话（打回说明），顾客看到的追问就用这句；
    不留则由系统按缺失字段自动生成，例如
    「人工客服看过这张工单了，还需要您补充：订单号、原因。直接回复即可。」

    这一步修订了原先「工单是快照、内容不可编辑」的原则：
    快照的目的是可追溯，不是不可变。改动只允许发生在 RETURNED 状态，
    且每次改动都留痕（revision / last_actor / version）。

并发安全：工单级乐观锁

    人工端两个人同时改同一张工单，后保存的会静默覆盖先保存的——
    这是最容易发生、也最难发现的事故。
    现在 ticket 带 version，保存时必须原样带回：

        版本对不上 → 409「这张工单已被他人修改（你看到的是 v0，当前是 v1），请刷新后重试」
        不传 version → 400，拒绝无锁更新

    两层保护：先比版本给一句人话，再靠 SQL 的
    `WHERE version = ?` 挡住「比较与更新之间」那几毫秒的竞态。
    前端收到 409 会自动刷新到最新内容，让客服重新确认后再存。

鉴权：只做人工端，且只做登录不做权限

    人工端：账号预置（不开放注册）+ BCrypt + session cookie，
            AuthInterceptor 保护 /api/tickets/** 与 /api/templates/**。
    顾客端：匿名，不需要登录。

    为什么两端差别这么大：
        客服本来就该看到全部工单，权限模型只有「登录 / 没登录」两档，
        做登录很便宜；
        顾客侧一旦要登录，每个接口都得校验「这个会话是不是你的」，
        漏一个就是越权——那是另一天的工作量。
        只做登录页不做归属校验，是安全剧场，比明说「没有鉴权」更危险。

    所以有意不做：注册、找回密码、角色分级、数据隔离。
    也请注意：session 存在内存里，**重启后端所有人要重新登录**；
    多实例部署需要 spring-session。

    另有一个已知口子：/api/chat/** 对顾客开放，
    知道 sessionId 就能读该会话的历史（刷新续接需要它）。
    正式系统应换成会话令牌。

一处例外：顾客确认

    信息不全（追问已达上限）的工单，不直接入队，
    而是把整理好的一句话交给顾客确认后才提交。

    理由：这是唯一能拿到「语义正确性」信号的渠道——
    basis 只证明引用没编造，防不住误读；而顾客是唯一知道原意的人。

    三条克制：
      只对红级启用——绿黄信息够用，多一步就是打扰，也必然被无脑点过
      确认的是**一句话摘要**，不是字段表——字段是给我们用的压缩表示
      摘要**可编辑**——可编辑的文本会迫使人至少扫一眼，勾选框不会

    开关：app.chat.confirm-before-ticket（默认 true，关掉即旧行为）

    也要说清楚它的局限：防不住「不看就点」。
    所以分级绝不因此放松，而是把 customerConfirmed 记在工单上，
    方便以后对比「确认过」与「未确认」两类工单的错误率——
    如果没差别，这一步就该撤。

它不承诺：
    判断对不对。
    分级只说明「信息够不够」，不说明「结论正确」。
    实测证实过：顾客说「你们这什么质量」，
    basis 确实是原文、校验全过，但 reason=质量问题 是误读，
    这张工单会算成绿。所以依据必须常驻显示，
    让误读有被看见的机会。

    给不出概率。
    没有标注数据时，任何「0.87」都不是概率而是修辞；
    即使有，校准也是模板局部的，跨模板不成立。

三个维度的可计算性不同，处理方式也不同：
    完备性 → 可决策性    可精确计算（比率 + 否决）
    忠实性              可逼近（依据子串校验），防不住误读
    自洽性              只提示，不参与定级

【七之补、已知缺口】
----------------------------------------------------------------

不是 bug，是没做的部分。写在这里，免得被当成已完成：

    图片上传没有实现
        image 字段在界面上只渲染「需人工补充」，
        没有上传接口，也没有静态资源映射。
        原先 application.yml 里的 app.upload-dir 已删除——
        留着一段没人读的配置比没有更糟。
        真要做：一个 POST /api/uploads + 静态映射，约 30 行。

    工单内容不可编辑
        只能改状态 / 指派 / 决策 / 回问埋点。
        这是刻意的：工单是快照，改内容应该走「作废重建」，
        而不是让同一张工单的 values 变来变去。

    没有鉴权、没有分页、没有导出
        单机课程设计，刻意不做（见 idea.txt 第十一节）。

    打回次数封顶 2 次，且没有"打回原因"的历史表
        工单上只保留最后一次打回说明（return_note），
        第二次打回会覆盖第一次。要完整历史得加一张 ticket_return 表。

    状态回执是「懒」的，没有推送
        顾客出单后前端每 4 秒轮询一次 /status，
        状态跨过节点（已受理 / 处理中 / 已解决 / 已关闭）才写一条回执，
        且靠 chat_session.last_notified_status 保证同一状态只回执一次。
        代价：顾客关掉页面就不会被通知，回来打开才看到。
        真要做：SSE 或消息队列 + 定时任务，两周项目里成本不划算。

    第二个模板的评测只做了 smoke
        电商售后工单承担全部定量评测；
        IT 报修模板只用于验证「同一套管道能适配不同结构」。

【八、实测发现的问题（都是真的跑出来的）】
----------------------------------------------------------------

    1 契约不一致
      mock 模板里写 decision_options，接口用 camelCase decisionOptions
      → 提交时被后端当作「决策项为空」拒绝。已统一并写进 mock/README。

    2 写文件带 BOM
      PowerShell 的 Set-Content -Encoding UTF8 会写 BOM，
      让 JSON 解析直接失败。改动 JSON 一律用不带 BOM 的写法。

    3 通用 prompt 里泄漏了电商假设
      固定文案写了「不要替顾客下结论」，
      换成 IT 报修模板时语义就错了（来报修的是同事）。
      → 改为中性的「用户」，并加了一个用「完全中性 schema」
        断言固定文案无业务词的测试。靠读代码看不出来。

    4 pattern 是双刃剑
      把设备编号的 pattern 写成「4 位数字」（真实值 PC-2031）后，
      模型没有硬填违规值，而是输出 null —— 管道没坏，
      但那个本来可用的值被静默吞掉了。
      后果链条很安静：字段变空 → 必填缺失 → 红级 → 追问 →
      而顾客早说过了，问不出来。

    5 追问在重复自己
      两次追问一字不差：为了帮您处理，还需要确认：订单号。
      顾客会觉得系统没在听。已改为按轮次换措辞。

    6 决策耗时 -242ms
      DATETIME 没有小数秒，MySQL 把 created_at 的 .757 秒
      四舍五入到下一秒，于是「创建时间」比代码里的 now 还晚。
      两处一起修：时间列改 DATETIME(3)，并把耗时夹到 >= 0。
      ——单元测试里 createdAt 与 now 同源，永远不会负，
        只有连真库才会暴露。这就是那 4 个集成测试存在的理由。

    7 请求 deepseek-chat，响应里 model 是 deepseek-flash
      该 key 背后可能有网关映射。未查清，涉及质量与计费，
      建议拿到 key 时确认一次。

【九、常见问题】
----------------------------------------------------------------

Q 一发起对话就返回「未配置 app.llm.api-key」
A 说明 api-key 是空的。仓库里不再带任何默认 key，
  application.yml 只有占位符 ${DEEPSEEK_API_KEY:}。
  解法：设 DEEPSEEK_API_KEY 环境变量（设完重启后端）。
  注意区分：启动本身不需要 key，报错只发生在真正调用模型时。

Q 改了 application.yml 但行为没变，或明明配了 key 却报「未配置」
A 八成是**旧进程还占着 8080**，你的请求打到了旧实例。
  `mvn spring-boot:run` 会 fork 一个 java 子进程，
  关掉终端或杀掉 mvn 进程**不一定带走它**。

  查谁占着：
      netstat -ano | findstr :8080
  杀掉（用上面查到的 PID）：
      taskkill /PID 19396 /F

  这个坑很阴：进程还在、接口还有响应，只是响应来自旧代码。
  判断方法：看启动日志里的 PID，和 netstat 里的 PID 对不上就是它。
Q 我拿到了 key，怎么用上
A 只设环境变量，不要改文件：
      $env:DEEPSEEK_API_KEY = 'sk-你的新key'
      mvn spring-boot:run
  application.yml 里的默认值请保持为空（${DEEPSEEK_API_KEY:}），
  这样 key 永远不会进入 git。

Q 启动报 AccessDeniedException，路径指向 maven-repository
A Maven 本地仓库不在项目目录里，被文件沙箱挡了。
  正常终端里跑 mvn 不受影响；若在受限环境里跑，
  需要放宽该路径的写权限。

Q pnpm : 无法将"pnpm"项识别为 cmdlet、函数、脚本文件或可运行程序的名称
A 你机器上没装 pnpm（只有 Node.js 自带的 npm）。
  三种做法任选：
    1) 直接用 npm：            npm run dev
       （依赖已经装好，不需要再 install）
    2) 用 corepack 启用 pnpm： corepack enable pnpm
    3) 全局安装：              npm i -g pnpm
  注意：本文档里出现的 pnpm 命令，首次安装依赖时都可以换成 npm。

Q 前端 npm run dev 报 ERR_PNPM_IGNORED_BUILDS 或依赖校验失败
A 那是 pnpm 的限制，npm 没有。改用 npm run dev 即可。
  如果坚持用 pnpm，见 web/README.md 的三种解法。

Q 工单列表是空的
A 还没生成过工单。去「对话」页选模板、发一句话。

Q 红色工单为什么也能指派、能解决
A 它不是错误状态。信息不全的工单照样要流转，
  只是提醒人工「先补信息再决策」。
  若把它做成死路，这张工单就永远处理不了。

Q 为什么没有流式输出
A 实测端到端 0.63~1.30 秒，模型输出是结构化 JSON，
  顾客看到的两句话（追问、出单提示）都由代码瞬时生成。
  流式在这个形态下没有可服务的东西。详见 tech-stack.md 第六节。
