前端 · 两个端
================================================================

本项目的前端是**两个端**，一套依赖：

    用户端   http://localhost:5173/         顾客与 AI 客服对话
    人工端   http://localhost:5173/agent/   人工批阅工单、配置模板

为什么这样分：
    顾客不该看到工单列表、字段定义、内部质量分级；
    人工也不该在同一个界面里被顾客的对话流干扰。
    两边要的信息完全不同，硬塞进一个导航里只会互相妨碍。

为什么不是一个仓库两个工程：
    两个端共用同一份 api 封装、DynamicForm、QualityBanner。
    拆成两个工程要么复制代码，要么引入 workspace，
    对两周项目来说维护成本高于收益。
    但「两个端」是真的：两个 html、两套 main、两套布局，
    用户端代码里不引用任何工单/模板页面。

【启动】
----------------------------------------------------------------

    # 终端 1：后端
    cd ..
    mvn spring-boot:run

    # 终端 2：前端
    cd web
    npm install       # 只需一次
    npm run dev

然后：
    用户端  http://localhost:5173/
    人工端  http://localhost:5173/agent/

    人工端需要登录，演示账号 zhangsan / lisi，初始密码 123456。
    顾客端不需要登录，直接就是对话界面。

⚠ 先看你机器上有没有 pnpm：
     PowerShell 里执行  where pnpm
     没有的话就用 npm —— npm 随 Node.js 一起来的，一定有。
     本仓库的依赖是用 pnpm 装的，但 npm run 一样能跑
     （它只是读 package.json 的 scripts，执行 node_modules/.bin/vite）。

⚠ 用 127.0.0.1 可能连不上：vite 默认绑 localhost（IPv6 的 ::1）。
   用 http://localhost:5173/ 打开即可，或者启动时加 --host 127.0.0.1。


----------------------------------------------------------------
【pnpm 11 的构建脚本门（用 npm 可忽略）】
----------------------------------------------------------------

pnpm 11 默认拦截依赖的安装脚本，并且每次 run 前做一次依赖校验，
校验不过就拒绝执行（ERR_PNPM_IGNORED_BUILDS）。
本项目已用 pnpm-workspace.yaml 关掉这两道门：

    verifyDepsBeforeRun: false

如果仍然报错，二选一：

    1) 交互批准一次（推荐，一劳永逸）
       pnpm approve-builds      # 勾选 esbuild

    2) 绕开 pnpm，直接用 node 调 vite
       node node_modules/vite/bin/vite.js

注：esbuild 的二进制由平台包 @esbuild/win32-x64 提供，
    安装脚本没跑也不影响构建——已实测通过。

【两端的信息边界（很重要）】
----------------------------------------------------------------

用户端只能拿到：
    GET  /api/chat/templates        能咨询哪几类问题（只有 id + 名称）
    POST /api/chat/sessions         开新会话
    POST /api/chat/sessions/{id}/messages   一轮对话
    POST /api/chat/sessions/{id}/confirm    确认后入队
    GET  /api/chat/sessions/{id}/status     工单状态回执（只回状态 + 决策 + 一句人话）

用户端**拿不到**：字段定义、决策项、质量分级、工单列表。

人工端**需要登录**才能调 /api/tickets/** 与 /api/templates/**：
    POST /api/auth/login    写 session cookie（前端不保存任何凭据）
    GET  /api/auth/me       前端启动时问一次「我是谁」
    POST /api/auth/logout   真的能退掉——这是选 session 而不是 token 的原因

    前端守卫只是体验层，可以被绕过；绕过之后接口仍会 401。
    真正的门在 AuthInterceptor。
（CONFIRM 响应里刻意不回 level：RED 是内部词汇，
 「信息不全」这件事由 missing 列表表达。）
出单后它只知道「已转人工」和工单号，看不到红黄绿——
顾客不需要知道我们内部是怎么判级别的。

人工端才有：
    GET/PATCH /api/tickets          列表与批阅
    GET/PUT   /api/templates        模板与字段
    POST      /api/templates/{id}/preview   试抽

判断有没有越界，看一个信号：**用户端出现「YELLOW」「缺必填」这类字样，
就是越界了。**


----------------------------------------------------------------
【三处与后端契约一致的地方，改前端时别踩】
----------------------------------------------------------------

1. 字段类型是**小写字符串**（text / enum / number / boolean / date / image），
   由后端 FieldType 的 @JsonValue 决定，用来驱动控件选择。

2. 级别是**大写** RED / YELLOW / GREEN，只在人工端出现。
   它表示的不是分数，而是「能不能直接决策」：
       RED    不可直接决策，需先补信息
              （来源有两种：追问超限仍缺必填，或人工打回 RETURNED）
       YELLOW 可决策，但请先核对依据
       GREEN  可直接决策

3. 保存工单必须带上读到的 `version`。
   版本对不上后端返回 409，前端会自动刷新到最新内容。
   别为了"省事"把 version 去掉——那正是静默丢更新的入口。

4. 工单详情里的 basis（原文依据）**始终显示**，不分级别。
   绿色只说明信息齐全，不说明判断正确。
   把依据藏起来，误读就永远没人发现。


----------------------------------------------------------------
【两条 UI 规则（来自设计文档）】
----------------------------------------------------------------

    分级绑定操作权限，不绑定分数
        所以界面上没有任何「68 分」这种数字，只有「缺哪两项」。

    颜色必须配文字与图标
        报告要黑白打印，纯颜色分级在纸上会消失。
