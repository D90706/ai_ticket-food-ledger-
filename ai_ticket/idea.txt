----------------------------------------------------------------
【一、原始构想（v1 原文，存档）】
----------------------------------------------------------------

AI客服，以淘宝举例子，用提示词以及rag技术约束AI的回答，使得回答
围绕着商品和客服的核心职能进行，同时给予AI一定的权限，例如处理基
础的商品介绍，顾客询问，当有复杂问题时则，将问题精炼为表单的形式
传递给人工客服（或老板）进行事物决定，如{顾客："1号"，业务："换
货",原因:"尺码过大"。证据："XXX"}，简化信息，方便人工快速决策。


----------------------------------------------------------------
【二、核心问题与定位】
----------------------------------------------------------------

2.1 原构想里真正的难点是什么

原构想的技术手段是「用提示词和 RAG 约束 AI 的回答」。
但手段不等于难点。拆开看，真正的难题只有两个：

    难点一：字段设计。
        自然语言 → 决策特征 的映射。
        抽多了是无效信息，抽少了是信息缺失。
        这需要业务知识，而不是编程能力。

    难点二：回答的可靠性。
        AI 一旦答错政策，就可能构成商家的承诺，
        成本是不对称的。

这两个难关有一个共同点：它们都源于「业务知识被写死在开发者手里」。
开发者不懂电商，就只能猜字段、猜话术。

于是得到一个关键判断：
    业务知识不应该由开发者提供，应该由领域用户提供。


2.2 定位收敛：从「回答问题」到「生成工单」

原构想里 AI 要做两件事：回答问题 + 生成工单。
重新评估这两半的价值与代价：

    回答问题这一半：
        价值低（顾客自己也能在详情页看到）
        风险高（承诺、合规、极限词）
        代价高（需要 RAG、知识库、召回、防幻觉）

    生成工单这一半：
        价值高（这是人工真正需要的）
        风险可控（抽错字段可以校验、可以兜底）
        代价低（只需要结构化输出）

所以定位收敛为：AI 只负责把对话压缩成工单。
回答能力作为可选项，交给模板里的知识块去承载（见 4.3）。

这一收敛带来三个直接结果：
    - 不再需要 RAG / 向量库 / embedding / 文档解析
    - 幻觉风险从「答错政策」缩小为「抽错字段」，可校验
    - 系统的产出物从「文本」变成「结构化数据」


2.3 最重要的一次抽象

    系统产出物：自由文本  →  结构化数据

这一步抽象是整套设计的支点。因为只有变成结构化数据，
才可能同时获得：可校验、可测试、可流转、可版本化。
一个聊得再好的客服机器人，产出仍然是一段文本，
它就永远无法被验证，也无法进入任何流程。

而结构化数据的 schema 从哪来？这就是设计权的归属问题。
把它交给领域用户，两个难点同时被解决：
字段由懂业务的人定义（难点一），
回答的边界由懂业务的人划定（难点二）。


2.4 一句话定位

    一个 Schema 驱动的对话式工单生成引擎——
    领域用户自定义字段与决策项，
    AI 将非结构化对话压缩为结构化、可决策的工单。

【三、整体架构】
----------------------------------------------------------------

四层。层与层之间只通过数据耦合，
且「模型的职责」与「代码的职责」被严格切开：

    一、模板层       领域配置包
        role / knowledge / decision_options
        fields（含必填与选填）
            │
            │  模板驱动 prompt
            ▼
    二、抽取层       只负责「看到什么」
        动态 Prompt → LLM
        → values / basis / suggestion / summary
        ★ 不输出置信度，不输出缺失清单
            │
            │  values + basis
            ▼
    三、核验层       只负责「够不够」
        纯代码，无模型，可单元测试
        完备性→可决策性 / 忠实性 / 自洽性 核验 → 分级
            │
            │  工单 + schema 快照 + 分级
            ▼
    四、工单层       人工决策
        分级提醒 / 状态机 / 指派 / 决策记录

这张图最重要的一处分界在第二、三层之间：

    模型只回答「这段对话里看到了什么」，
    代码只回答「这些够不够用」。

为什么必须这样切：模型的自我评价不可靠（实测证明，见 9.1）。
一旦让模型同时承担「抽取」和「评价自己的抽取质量」，
它的评价就会污染它的抽取。

设计要点：抽取层对任何模板都是同一套代码。
「通用性」体现在抽取层与模板解耦，而不是体现在功能数量上。


----------------------------------------------------------------
【四、模板：一个完整的领域配置包】
----------------------------------------------------------------

4.1 模板的结构

模板不只是字段表。它是某个业务领域的完整配置，
包含「AI 扮演谁」「AI 知道什么」「能给出哪些决策」「要产出哪些字段」：

{
  "name": "电商售后工单",
  "version": 1,
  "role": "你是服装店的售后助手，语气克制，不承诺赔付",
  "knowledge": "【退换货政策】7天无理由……【尺码表】M 码适合165-170……",
  "decision_options": [
    "批准换货", "批准退货", "拒绝", "要求补证", "转售后专岗"
  ],
  "fields": [
    {"key":"order_id","label":"订单号","type":"text","required":true},
    {"key":"reason","label":"原因","type":"enum","required":true,
     "options":["尺码不合适","质量问题","发错货","其他"]},
    {"key":"worn","label":"是否已穿着","type":"boolean","required":false},
    {"key":"evidence","label":"证据照片","type":"image","required":false}
  ]
}

每个字段上的 required 不是一个普通的勾选框。
它同时决定了三件事：AI 要不要追问、工单级别怎么定、工单是什么颜色。
详见 4.4。


4.2 为什么决策项要由模板定义，而不是让 AI 自由生成

如果让 AI 自己决定「建议怎么处理」，它给出的就是一段自由文本建议，
人工仍然要自己判断，压缩的价值没有落地。

把 decision_options 做成模板里的枚举，意味着：
    - 决策是有限的、可枚举的、可统计的
    - AI 只能从给定选项里选，不会发明处理方式
    - 决策权限的边界由业务方划定，而不是交给模型

这实际上是把「AI 的权限」变成了一份白名单。
比在提示词里写「你没有退款权限」可靠得多。


4.3 为什么 knowledge 用全量注入，而不是检索

模板里的 knowledge 是用户自己填写的领域知识文本（通常几千字）。

    检索方案的代价：切分、embedding、向量库、召回调优，
                    以及召回失败带来的错误回答。
    全量注入的代价：几乎为零。

在几千字的量级上，全量注入的召回率是 100%，
且少了一整层可能出错的组件。所以这里的取舍很清晰：
用最简单的实现拿到最好的效果。

设计上仍然保留 Retriever 抽象（见第十节），
将来语料涨到十万字时，换成向量检索只改一个实现类。

顺带的好处：knowledge 由用户填写，
等于把「AI 能不能回答、能回答到什么程度」也交给了用户。


4.4 必填与选填：字段设计里最重要的一个勾选

required 这一位看起来最不起眼，但它是整套设计的枢纽：

    必填字段为空              →  触发追问
    必填字段为空且追问超限      →  工单标红，提示人工补信息
    选填字段为空              →  只影响颜色，不影响出单

也就是说，模板作者勾选「必填」这个动作，
实际上是在定义「什么情况下 AI 有权继续问下去」。
这是业务决策，不是技术配置。

▍四条设计规则

规则一：必填的含义是「缺失即无法决策」，不是「比较重要」。
    判定方法就是 6.2 的必要性检验：
    这个字段为 null 时，人还能做出决定吗？
    能 → 选填；不能 → 必填。
    把「希望有」写成必填，会让工单永远停在追问阶段。

规则二：必填项必须可获。
    如果一个字段在某些场景下天然不存在，它就不能是必填。
    典型反例来自实测：IT 报修模板把「设备编号」设为必填，
    但「三楼会议室 Wi-Fi 全断」这种故障根本没有设备编号。
    结果这张工单永远缺一个问不出来的字段，永久卡死。

    → 推论：必填项必须用 6.2 的可获性检验过一遍，
      并且必须配套追问出口（见 7.3）。

规则三：必填项数量控制在 3～5 个。
    太少 → 工单信息不足，人工仍要回头问顾客；
    太多 → 追问链变长，顾客在对话阶段就流失了。
    必填项的数量，本质上是在「工单质量」与「对话完成率」之间取平衡。

规则四：选填不是「次要」，而是「缺失仍可决策」。
    它决定的是工单的级别：选填全齐 → 绿，缺几项 → 黄。
    所以选填项的价值在于「提升可决策的把握」，不在于「阻断流程」。


----------------------------------------------------------------
【五、字段设计权归属用户】
----------------------------------------------------------------

5.1 设计理由

字段设计是这套系统里唯一需要业务知识的环节，
而开发者恰恰没有业务知识。

两条路：
    A. 开发者预设字段  → 换个业务就作废，且一定设计不好
    B. 用户自己定义    → 领域知识天然到位，系统可跨业务复用

选 B。这也顺带把「字段设计需要专业人士」这个质疑正面解决了：
专业的人本来就在用户那边。

于是系统的通用性不再依赖开发者懂多少行当，
而依赖 schema 是否被彻底数据化。


5.2 用户可以做的

    - 增加 / 删除字段
    - 修改字段名、类型、枚举选项
    - 设置每个字段是必填还是选填   ← 见 4.4
    - 调整字段顺序
    - 维护决策选项列表
    - 编辑 role 与 knowledge 文本
    - 整模板 JSON 导入 / 导出

一个工程约定：整个模板用一个接口整体提交，
不做字段级 CRUD。前端维护本地 json，改完整体保存。
理由：字段级 CRUD 会让后端多出一整套接口和状态，
而整体提交在语义上更符合「模板是一个整体」。


5.3 设计与非设计的分界线

这是本设计里最需要克制的地方。
「字段可配置」到「字段设计器」之间，混着一整个前端产品：

    可配置：schema 是数据不是代码        ← 架构能力
    设计器：用户用图形界面从零创造 schema ← 产品功能

前者是这套设计必须要的（否则无法跨业务），
后者是本期明确不做的（见第十一节）。

所以字段编辑采用表格 + 行内编辑 + 上移下移按钮，
不做拖拽、不做布局、不做条件显示。
这不只是工期考虑，也是设计上的判断：
布局与联动属于「表单设计器」的范畴，
而本系统的核心价值在「对话 → 结构化」这一侧，
不在表单本身长什么样。


----------------------------------------------------------------
【六、字段设计方法论】
----------------------------------------------------------------

6.1 原则：字段从决策倒推，而不是从对话里抽

错误的做法：读一堆对话，看里面有哪些信息，拼成字段表。
    结果必然又缺又多，因为「对话里有什么」和
    「决策需要什么」是两个集合。

正确的做法：先问人工要做哪些决策，再问每个决策必须知道什么。

    Step 1  列出决策枚举（5～7 个，不要多）
                例：批准换货 / 批准退货 / 拒绝 / 要求补证 / 转售后专岗

    Step 2  对每个决策列「必须知道什么」
                以「批准换货」为例：订单号、是否在7天无理由内、
                是否影响二次销售、责任归属、目标SKU是否有货、
                运费谁承担

    Step 3  用三个检验筛掉不该留的（见 6.2）

    Step 4  字段分层（见 6.3）

这一步的意义：它把「字段设计」从依赖专家直觉，
变成了一个可复现的、任何人都能执行的流程。
有流程，用户自己就能定义一个模板。


6.2 三个检验

检验一：必要性  ——  治「信息缺失」，同时决定必填还是选填
    问：该字段为 null 时，人还能做决定吗？
    能   → 选填
    不能 → 必填槽位，AI 必须追问到为止
    这条检验是 required 这个勾选框的唯一依据。

检验二：敏感性  ——  治「无效信息」
    问：该字段取值变化，决定会变吗？
    不变 → 删掉
    会变 → 保留
    这条检验的意义：一个不影响决策的字段，无论抽取多准，
    都是纯粹的成本（多占 prompt、多一个出错点、多一栏干扰人）。

检验三：可获性
    问：AI 能从对话里可靠抽出来吗？
    抽不出       → 转为「向顾客追问项」
    追问也问不到 → 删掉，或从必填改为选填
    这条检验把「字段设计」和「对话能力」连接起来：
    字段的价值取决于它能否被问出来。
    它也是 4.4 规则二的检验手段。


6.3 字段分层

不要把所有字段平铺成一列，按用途分四层：

    L1 决策字段（必填，枚举优先） → 驱动人工决策
    L2 说明字段（自由文本）       → 给人读，不参与判断
    L3 派生字段（代码计算）       → 优先级、时效、建议动作
    L4 元字段                    → 三维核验结果、缺失清单、对话链接

分层的意义：只有 L1 需要 AI 精确抽取，
L2 抽得口语化一点没关系，L3 由代码算不用抽。
把「必须准」的范围压到最小，是提高整体准确率最有效的手段。

注意 L4：三维核验结果与缺失清单属于元数据，
由核验层计算（见第九节），不由模型输出。


6.4 两条硬规则

规则一：能枚举的，绝不留自由文本。

    原因字段应该是：
        reason_code: ENUM   +   reason_text: 可选自由文本

    理由：自由文本不能驱动决策、不能校验、不能统计。
    人看一段话做判断，和人对着一组枚举做判断，
    后者快且一致。压缩的价值正来自「从文本到枚举」这一步。

    附加要求：枚举值必须附带原文依据（basis）。
    理由见 9.5——这是发现「误读」的唯一免费手段。

规则二：每个字段都必须显式声明必填或选填，不允许有默认值。

    模板作者必须对每一个字段做一次判断：
    它缺了，人还能决策吗？
    这个强制动作本身，就是对模板设计质量的最低保障。

    一个字段如果连设计者都说不清该不该必填，
    那它大概率应该被删掉（回到检验二）。


----------------------------------------------------------------
【七、抽取管道与追问闭环】
----------------------------------------------------------------

7.1 管道

    用户对话
        ↓
    动态 Prompt 生成（由模板拼装）
        ↓
    抽取层：LLM 输出 values / basis / suggestion / summary
        ↓
    核验层：从 values 推导缺失 → 按 schema 分必填/选填 → 评分分级
        ↓
    判定
        ├─ 必填缺失     → 生成一句追问，回到对话
        ├─ 追问超限     → 强制出单，标红「信息不全」
        └─ 必填齐全     → 出工单（写入 schema 快照）
                              ↓
                        人工在工单层决策

为什么校验与重试必须在管道里，而不是信任模型：
    结构化的前提是可校验。模型输出 JSON 的稳定性永远不是 100%，
    所以「校验 → 失败 → 重试」是这条管道的一部分，
    而不是异常处理。


7.2 缺失判定：以 values 为准，不以模型的自我描述为准

实测中发现过一个典型失效：
模型输出的缺失清单漏了一项（values 里有 3 个空值，清单只报了 2 个）。

所以缺失判定只能有一条依据：

    缺失 = schema 中所有字段 减去 values 中非空的字段

    然后按 schema 的 required 分流：
        missing_required = 缺失 ∩ 必填
        missing_optional = 缺失 ∩ 选填

这条规则的意义：它把「缺不缺」变成了一次集合运算，
     完全确定、完全可测、与模型的表述无关。

顺带一个设计后果：既然缺失可以算出来，
     模型就不再需要输出缺失清单，也不必自我评价。
     抽取层的输出因此收缩为四个字段（见 7.4），
     模型只做一件事，失败模式也随之减少。


7.3 追问闭环

    必填缺失且追问次数 < 2   → 生成一句追问，等用户补充
    必填缺失且追问次数 >= 2  → 强制出单，标红「信息不全」
    必填齐全                 → 出工单

为什么必须留「追问超限」这个出口：
    必填项并不总是可获得的（见 4.4 规则二）。
    「会议室 Wi-Fi 全断」没有设备编号，
    如果没有这个出口，这张工单会永久停在追问状态，
    既出不来，也无人知晓——这比出一张残缺工单更糟。

    追问超限的意义是：把「没有出口的死循环」
    变成「有出口的降级」，并且让缺口显式暴露给人。

追问的措辞由字段的 label 生成，不由模型生成。
理由：追问只需要问清楚「缺什么」，这是一次确定性拼装，
    交给模型只会引入不必要的波动。

▍追问超限之后：先让顾客确认，再入队

红级工单意味着「人工还得回头问顾客」。在它进入人工队列之前，
把整理好的一句话交给顾客看一眼，是整个系统里唯一能拿到
「语义正确性」信号的渠道——basis 校验只能证明引用没编造，
防不住误读；而顾客是唯一知道原意的人。

三条克制：

    只对红级启用
        绿黄信息够用，多一步就是打扰，而且必然被无脑点过。

    让顾客确认一句话，而不是字段表
        字段是给我们用的压缩表示，顾客读的是话。
        读句子是本能，读结构不是。
        摘要缺失时用已抽到的字段兜底拼一句，不能给顾客一张空白卡。

    摘要可编辑，不是勾选
        可编辑的文本会迫使人至少扫一眼；
        「确认 / 取消」两个按钮不会。

它防不住什么，也要写下来：

    防不住橡皮图章。九成的人不看就点，这道防线就退化成了责任转移，
    而不是质量提升。所以：

        分级绝不因为「顾客确认过」而放松——
        确认改变的是「谁对内容负责」，不是「内容一定对」。
        工单上记录 customerConfirmed，让这一步到底有没有用可被验证：
        对比确认过与未确认的工单，人工抽查时内容不符的比例有没有下降。
        如果没有差别，就应该撤掉它。

    这也是本设计的一贯态度：功能要能被证伪，否则就是装饰。

    一条实现上的取舍：顾客在待确认状态又说了话，当作补充信息重新抽取——
    补一句可能就够了，那就直出，不必再确认。
    确认不是一道闸门，是「还差一点」时的一次停顿。

▍人工处理完之后，顾客怎么知道

工单交接出去之后，最伤体验的不是处理慢，是**一片沉默**。
顾客不知道自己那张单子有没有人看、看到哪一步了。

所以要在状态跨过节点时回执一次。三个刻意的决定：

    不为它调用模型
        工单状态是确定性的数据库字段。
        让模型去「检查」，只会多一次调用、多一次说错的机会
        （它完全可能把 ASSIGNED 编成「已解决」）。
        状态由数据库给，文案由代码拼——和追问话术同一个道理。

    回执幂等，落库只写一次
        会话上记 last_notified_status，只有状态真的变了才写一条消息。
        否则顾客每次轮询都会刷出一条「已受理」，
        那不是通知，是噪音。

    只通知「人工真的动过」的状态
        PENDING 与 INFO_INCOMPLETE 是生成时的初始状态，
        顾客在出单那一刻已经被告知过了，再通知就是重复。

通知是「懒」的：顾客来问才写，没有推送。
换来的是两周项目里不必引入长连接与调度器。
代价写进已知缺口——顾客关掉页面就不会被通知，回来才看到。
这个取舍要说清楚，不能假装是实时通知。

▍人工处理不了的时候：打回，而不是硬着头皮结单

红级工单进了人工队列，人工看到「缺订单号」——然后呢？
原来的设计只留了「回问率」这个埋点，也就是人工自己想办法联系顾客。
可人工根本没有顾客的联系方式。这是一条断掉的链路。

所以要有打回：工单退回到顾客那边，补齐了再交上来。

三个决定：

    原地补全，不新建工单
        顾客只该认一个单号。"再提交"这三个字就说明了他期待的是同一张单。
        新建一张会让顾客看到两个单号，还要人去解释哪个是哪个。

    这修订了「工单是快照，不可编辑」这条原则
        必须承认这是修订，不能悄悄改。
        快照的目的是可追溯，不是不可变。所以把可追溯拆成三件具体的东西：
            revision 每改一次 +1（第几版内容）
            last_actor 记下是谁触发的
            version 乐观锁保证不会两个人同时改
        这三件事都在，可追溯性就没有丢，只是不再靠"不可变"这条更粗的手段。
        而且改动被限死在 RETURNED 状态：一张正常工单仍然不能被悄悄改写。

    打回要封顶
        同一张单最多打回 2 次。否则会出现「人工踢给顾客、顾客补不出来、
        人工再踢」的死循环，最后这张单永远悬着。
        到顶之后的正确出路是：人工自己处理，或者关闭并说明原因。

    追问预算要重置
        打回是人工明确要求补全，所以顾客回答时应该重新拥有完整的追问机会。
        不重置的话，顾客刚要开口，AI 就把他推到"确认后提交"的卡片上了——
        那是在催他确认一份他自己知道不全的东西。

还有一条细节值得记下来：打回的追问不能写两遍。
对话层的 ReturnFlow 会把「需要补什么」写进会话，
状态回执如果也拼一条相似的话，顾客会收到两条几乎一样的信息。
所以回执直接把会话里那条消息带回去，不再重复落库。
两个模块都能"往对话里说话"时，就得指定一个唯一来源。
▍并发：两个人同时改一张工单

这不是"多客服才需要"的功能，是单客服之外必然发生的事：
主管看一下、客服改一下，两个人手上是同一张单。

原来的写法是读出来、改字段、整行覆盖。
两个人先后保存，后写的会把先写的**静默吃掉**——
两边都以为自己成功了。这是最难查的一类事故，
因为它不报错、不留痕，只在几天后表现为"这单怎么变成这样了"。

所以工单带一个版本号，保存时原样带回：
    版本对不上 → 409，并且明确告诉你「你看到的是 v0，当前是 v1」
    不传版本   → 400，拒绝无锁更新

两层：先比版本给一句人话，再靠 SQL 的 WHERE version = ?
挡住"比较与更新之间"那几毫秒。只靠第一层是 check-then-act，
在并发下必然有窗口——这是基础知识，不该省。

▍鉴权：为什么只做人工端，且只做登录不做权限

关键区别不是"登录难"，是两端的**权限模型复杂度差一个量级**：

    人工端：客服本来就该看到全部工单，
            权限只有「登录 / 没登录」两档 → 一个拦截器就够。

    顾客端：一旦要登录，每个接口都得回答
            「这个会话是不是你的、这张工单能不能给你看」。
            漏一个就是越权。那是真正的工作量，不在登录页上。

只做登录页、不做归属校验，是安全剧场：
它给评审一种"有安全措施"的错觉，比明说"没有鉴权"更危险。

所以：

    人工端做   预置账号（不开放注册）+ BCrypt + session cookie
    顾客端不做 匿名接入，靠「工单号 + 联系方式」找回，而不是账号

用 session 不用 JWT，也是同一个判断：
单机课程设计没有多实例、没有跨域、没有移动端，
JWT 的收益一个都拿不到，代价却是**不能真正注销**——
客服在公共电脑上登过就退不掉。

不做的事要写清楚，别让它看起来像忘了：
    注册、找回密码、角色分级、数据隔离——有意不做
    session 在内存里，重启后端所有人要重新登录
    /api/chat/** 对顾客开放，知道 sessionId 就能读该会话历史
    （刷新续接需要它；正式系统应换成会话令牌）7.4 抽取层的输出契约

四个字段，一个不多：

    {
      "values":     { "reason": "质量问题" },        ← 字段值
      "basis":      { "reason": "你们这什么质量？" }, ← 原文依据
      "suggestion": "批准换货" 或 null,              ← 建议决策
      "summary":    "顾客称袖口有划痕、缝线不齐，情绪较激烈"
    }

四个字段各自的理由：

    values
        抽取的产物，唯一的事实来源。

    basis
        枚举值的原文依据。它不是可选装饰，
        而是让「误读」可被发现的手段（见 9.5）。

    suggestion
        从模板的 decision_options 里选一个。
        注意：它只是「建议」，放行权在核验层（见 9.4）。

    summary
        一句话概述，不参与决策。
        存在的理由：schema 永远无法穷尽对话里的信息，
        顾客的情绪、未被字段覆盖的描述都需要一个落点。
        没有它，那些信息在压缩过程中就永久丢失了。

明确不输出的两个字段：

    confidence —— 模型的自我评价，实测与信息完整度无关（见 9.1）。
    missing_slots —— 可以由 values 与 schema 算出，且模型会算漏（见 7.2）。

这一取舍的本质：把「评价」从模型的职责里拿掉，
    只留给它「观察」。模型的强项是抽取，不是审计自己。


7.5 动态 Prompt 的结构

    输入：模板（role + knowledge + decision_options + fields）
    拼装顺序：
        1. 角色（role）
        2. 领域知识（knowledge 全文注入）
        3. 可用决策选项（明确列出，禁止自创）
        4. 字段清单（key / 中文名 / 类型 / 必填或选填 / 枚举值）
        5. 输出格式（严格 JSON，四个字段）
        6. 硬规则：
             无法确定 → 填 null，禁止编造、禁止用常识补全
             enum 只能取给定值
             enum 非 null 时必须给出基原文的 basis
        7. few-shot 示例  ← 由 schema 自动生成

其中第 7 条是关键技巧：

    按每个字段的类型自动填一个合法值，拼成一条示例 JSON。
    成本极低，但显著提升任意 schema 的抽取稳定性。

这一条为什么重要：因为字段是用户定义的，
开发者无法为每个模板手写示例。
自动生成示例，是让「通用」在准确率上不付代价的办法。
这也是「字段设计权归用户」这个主张能成立的技术前提之一——
如果每个新模板都需要人工调试 prompt，
那通用就是假的。

▍一条硬约束：固定文案里不许出现业务词

prompt 由两部分组成：模板注入的内容 + 拼装的固定文案。
后者必须与业务完全无关，否则「通用」就是一句空话。

实测抓到过一个例子：硬规则里原本写「不要替用户下结论」，
更早的版本写的是「不要替顾客下结论」——
换成 IT 报修模板时这句话就错了，来报修的是同事，不是顾客。
这是电商假设悄悄焊进了通用文案，已改为中性的「用户」。

更值得记的是：这条约束是可测的。
用一个完全没有业务含义的模板（字段叫 f1/f2、角色只写「你是助手」）
拼一次 prompt，断言里面不出现「订单/售后/退款/商品/顾客/换货/报修」。
测试通过了，通用性才是真的；靠读代码是看不出来的。


----------------------------------------------------------------
【八、Schema 版本化：这套设计必须提前解决的问题】
----------------------------------------------------------------

问题：用户随时可以增删改字段。
      那么已经生成的历史工单，按新 schema 渲染就会出错。

两个必须的设计决定：

    1. 模板带 version，每次修改字段即递增
    2. 工单保存 schema_snapshot —— 生成那一刻的完整 schema json

工单结构：
    id
    template_id
    template_version
    schema_snapshot    JSON    ← 渲染工单时用它，永不回查当前模板
    values             JSON    ← 抽取层的产物
    basis              JSON    ← 枚举值的原文依据
    summary            text    ← 说明字段
    quality_level      ENUM    ← 红 / 黄 / 绿（见第九节）
    quality_detail     JSON    ← 三个维度的核验明细与原因句子
    needs_clarify      boolean ← 人工点了「需联系顾客」，生产环境埋点
    decision_time_ms   int     ← 决策耗时，可自动记录
    status             ENUM    ← 含「信息不全」
    assignee
    decision           ← 人工最终决定
    session_id
    created_at

核心原则：工单永远带着自己的 schema 渲染，不依赖模板的当前状态。

这不是防御性编程，而是「可配置」这个设计的必然推论：
一旦把字段的定义权交给用户，就必须同时接管字段的演化史。
否则「自由设计」只是一个会在两周后出错的承诺。

附带的收益：schema 快照让「同一张工单当时是按什么规则生成的」
成为可追溯的事实，这在对账、复盘、责任认定上都有意义。

状态机（固定，不做编排）：
    待处理 → 已指派 → 处理中 → 已解决 / 已关闭（+ 驳回重开）
    信息不全 —— 必填缺失但追问超限时强制出单，仍可被指派与处理


----------------------------------------------------------------
【九、工单质量：三个维度与分级】
----------------------------------------------------------------

9.1 这个词必须放弃：「置信度」

一开始的方案是让模型在输出里带一个 confidence 用于熔断。
实测否掉了它：

    缺 1 个必填项 → confidence 0.75，并且给出了决策建议
    缺 2 个必填项 → confidence 0.70
    缺 2 个必填项 → confidence 0.50

缺得少的不一定给得低，缺得多的也不一定给得低。
更糟的是「缺必填项 + 高置信度 + 仍给出建议」这个组合，
会带着一个看起来很自信的错误建议流到人工手里。

原因很直白：模型度量的是「它对自己填的那些值有多确定」，
而流程需要知道的是「这张工单够不够做决策」。
两个不同的量，不能互相代理。

但问题不只是「谁来算」。真正的困惑来自这个词本身：

    「置信度」预设了一个可测量的真值，
    于是你永远在问「这个数字对不对」，
    而这个问题没有答案（见 9.3）。

所以这个词要被切开。切开之后，每个部分的答案都很清楚。


9.2 把「置信度」切成三个维度

一张工单要经得起三个不同的追问：

    维度一  完备性 → 可决策性  ——  填了多少？够不够做决定？
    维度二  忠实性            ——  填进去的值是否忠于对话？
    维度三  自洽性            ——  工单内部是否互相矛盾？

三者对应三种失败，而且失败的样子完全不同：

    可决策性失败  →  工单是「空的」，人工得回去问顾客
    忠实性失败    →  工单是「满的」，但里面的值可能是错的
    自洽性失败    →  单个字段都对，合起来自相矛盾

最容易漏掉的是忠实性：一张看起来齐全的工单，
可能每一条都填错了，而人工不会有任何警觉。
这比空工单危险得多——空缺会被发现，错误不会被发现。

▍三个维度下的子项与可计算性

    维度一  完备性 → 可决策性
        字段填充率                  可算，连续量
        必填满足率                  可算
        选填覆盖率                  可算，连续量
        这些够不够做决定            判据可算，结论依赖决策类型

    维度二  忠实性
        值是否符合字段定义          可算（enum / 类型 / pattern）
        是否给出原文依据            可算
        依据是否为原文子串          可算
        依据是否真的支持该值        算不出来

    维度三  自洽性
        值域与格式的内部冲突        部分可算
        字段间的业务规则冲突        算不出来

▍完备性不是第四个维度，而是第一个维度的度量面

完备性与另外两个维度是部分重叠的，但不是冲突的：

    重叠在于：它贡献了可决策性的全部输入。
        必填缺了 → 不可决策。所以完备性是可决策性的「因」，
        把它抽出去，可决策性就没有依据了。

    不冲突在于：它还有一个可决策性回答不了的问题——
        「这个模板的字段设计本身合不合理？」
        这个问题与工单无关，只与模板有关（见 9.4 的四象限）。

所以正确的处理不是删掉它，而是给它一个确切的位置：
    完备性是可精确计算的度量，可决策性是由它导出的判定。

这个分解的意义在于：它把一个无解的问题
（「这个数字准不准」）换成了三个各有答案的问题。
其中前两个维度的大部分子项都能确定性计算，
只有「依据是否真的支持该值」和「业务规则是否冲突」算不出来——
而这两项恰好对应本设计承认能力边界的位置（见 9.5、9.6）。


9.3 为什么给不出一个概率

三层理由，一层比一层硬：

第一层：没有标注数据。
    要说「这张工单正确率 87%」，先得有一批人工标过的工单
    验算出 87% 这个比例。没有数据时给出 0.87，
    它不是概率，它是修辞。

第二层：即使有数据，校准也是模板局部的。
    电商模板上校准出的「85 分 = 90% 正确」，
    搬到 IT 报修模板上完全不成立——
    字段类型分布、枚举歧义程度、对话风格全变了。
    不存在一个跨模板通用的、有概率意义的分数。

第三层：正确性本身不是良定义的随机变量。
    「reason 抽得对不对」取决于业务口径。
    「尺码不合适」和「质量问题」，
    同一句话在不同店铺可能归不同类。
    没有唯一正确答案，就没有频率可估。

结论：不要试图算概率。
    能算的是「缺陷」，能产出的是「分级预警」。
    这两件事是可解的、可测的、可解释的，
    而且对人工比一个分数更有用。


9.4 维度一 · 完备性与可决策性：度量用比率，判定用否决

这个维度里有两件事，必须分开说：

    完备性   ——  填了多少        度量，连续，可精确计算
    可决策性 ——  够不够做决定     判定，离散，依赖决策类型

两者相关，但其中一个推不出另一个。

▍完备性：三个可精确计算的比率

    字段填充率   = 已填字段数 / schema 字段总数
    必填满足率   = 已填必填数 / 必填总数
    选填覆盖率   = 已填选填数 / 选填总数

三个都是纯集合运算，与模型无关，而且是连续量。
连续量的意义是它可以衡量趋势，而判定不能——
「这周平均填充率从 61% 升到 74%」是一句有意义的话，
「这周平均级别从黄变成绿」不是。

▍完备性高，不等于可决策

反例：模板有 12 个字段，填了 11 个，缺的恰好是订单号。

    字段填充率 = 92%    看起来很完备
    必填满足率 = 0%     完全不可决策

反向也成立：模板只有 3 个必填字段，全填上，
填充率不到 30%，但工单完全可决策。

所以完备性是可决策性的必要不充分条件。
把这两个合成为一个数，会同时损失两件事：
既看不清「到底填了多少」，也看不清「到底能不能用」。

▍完备性的第二个用途：模板体检

这是它不能被删掉的真正理由。
完备性不只在描述工单，它同时在描述模板：

    完备性低 + 可决策性通过
        选填字段设了一堆没人填 → 回 6.2 敏感性检验，删掉

    完备性高 + 可决策性不通过
        关键字段被设成了选填 → required 标错了，必须改

    完备性高 + 可决策性通过
        模板与工单都健康

    完备性低 + 可决策性不通过
        正常的红，模板没问题，等追问或补信息

同一张四象限表，横轴是工单，纵轴其实是模板设计质量。
所以完备性检验的对象不只有工单，还有模板——
这就是它与另外两个维度「部分重叠但不冲突」的确切含义。

▍可决策性：判据可算，结论是否决式

判据是确定的：必填齐全 → 通过；否则 → 不通过。没有中间态。

最初写的是线性加权（缺必填 -35、缺选填 -5……）。
这个写法有一个语义错误：

    缺 2 个选填（-10）和缺 1 个必填（-35）
    被放在同一个尺度上相加。

    但前者是「质量略有损失」，后者是「这张工单不可用」。
    它们不是数量差异，是种类差异。

线性加权会让「缺 1 个必填但其他全对」的工单拿到 65 分，
看起来像「还行」。它不是还行，它是不能用。

所以改成三档缺陷分类，不同档的处理方式不同：

▍A 阻断级（一票否决 → 红）

    必填字段缺失                  无法做决策
    enum 值不在候选内              值不可信，视为抽取失败
    类型不匹配 / 日期格式非法       数据坏了
    非 null 的 enum 完全没有依据    无据可查

任意一条命中即判红，不再进入后续判断。

▍B 降级级（→ 黄）

    依据不是对话原文的子串（编造引用）
    依据存在但不包含该信息
    选填字段缺失
    summary 为空

任意一条命中即判黄。

▍C 提示级（只打标，不改变级别）

    枚举值属推断而非对话中的陈述
    摘要与字段可能存在张力

▍为什么否决制比加权更对

    「能不能决策」本质上是一个门槛，不是连续量。
    门槛用否决，连续量用加权。
    混用会同时失去两者的好处：
    既没有一个清晰的可用/不可用分界，
    也没有一个可信的连续程度。

▍级别与严重度是两个正交的东西

    级别：由缺陷的「种类」决定（红/黄/绿）
    严重度：由缺陷的「数量」决定（用于列表排序、提示文案）

两者分开，不合成一个分数。
这样既保住了「阈值清晰」，又保住了「多的更靠前」，
而不需要任何伪造精度的数字。

分级的作用是提醒真实的人：这份信息到底够不够。
所以颜色不只是装饰，它直接决定人工能做什么：

    红  不可直接决策 → 决策按钮置灰，必须先补信息
    黄  可决策但需核对 → 强制勾选「已核对依据」才能点
    绿  可直接决策

规则固定写死在代码里，不向模板作者开放权重配置
（理由见第十一节：又一个「可配置」的无底洞）。


9.5 维度二 · 忠实性：三种依据校验与它的能力边界

忠实性不可直接计算，但可以用「依据」逼近。
对每个非 null 的 enum（建议扩展到所有非 null 字段）要求给出 basis：

    顾客原话：我收到的M码太大了，想换S
    reason  ：尺码不合适
    basis   ："我收到的M码太大了，想换S"

基于 basis 可以确定性做三件事：

    校验一  依据是否存在          basis 缺失 → 降级
    校验二  依据是否为原文子串     dialogue.contains(basis) 为假 → 降级
    校验三  依据覆盖率            有依据的字段数 / 非 null 字段数

校验二是这里最有价值的一条。

它把「模型是否编造了引用」变成一次字符串包含判断。
模型可以编字段值，但很难在编值的同时逐字引用原文。
所以「依据不是原文子串」是一个极廉价的可信度信号，
代价只是一次 contains()。

▍必须说清楚的边界：忠实性只被逼近，没有被验证

    顾客说：「你们这什么质量？」
    basis = "你们这什么质量"   ← 确实是原文子串，三项校验全过
    reason = "质量问题"        ← 但这是误读

这张工单在忠实性维度上会判定通过。

所以忠实性的能力边界是：

    能防「编造引用」，防不住「误读」。
    能证明「有据」，不能证明「据足以支撑这个值」。

这个边界不是实现的缺陷，而是「语义正确」这件事本身
不可被字符串运算判定的必然结果。

由此得到一条硬性展示规则（见 9.9）：
依据必须常驻可见，因为它是发现误读的唯一入口。


9.6 维度三 · 自洽性：通用规则可算，业务规则不碰

自洽性问的是「字段之间合不合得来」。这里要划一条线：

▍可算的：与业务无关的通用规则

    date 字段不得晚于今天（明显错误）
    date 字段早于对话发生的日期（明显错误）
    summary 非空（工单必须有个可读的概述）
    有值的字段必须都在 schema 内（不允许多余键）
    值的类型必须与声明一致

▍不可算的：需要业务知识的字段间规则

    「尺码不合适」应当建议换货而不是退货
    「质量问题」的运费应由卖家承担
    「影响面为全公司」的事件必须 30 分钟内响应

这些规则确实存在，而且确实重要，
但它们需要一个业务规则表达式的执行引擎。

本设计明确不碰：
    它会把项目从「对话 → 结构化」变成「对话 → 规则引擎」，
    而后者的复杂度不在这套设计的射程内。

所以自洽性只做两件事：
    通用规则命中 → 计入降级级
    业务规则     → 不做，留给人工的判断力


9.7 三类免费的确定性校验

这三项都能 100% 检出，都不需要模型，建议直接进模板结构：

▍一、字段级 pattern（正则）

    {"key":"order_id","label":"订单号","type":"text",
     "required":true,"pattern":"^\\d{8,20}$"}

    {"key":"device_no","label":"设备编号","type":"text",
     "required":true,"pattern":"^PC-\\d{4}$"}

不匹配 → 判为抽取错误，走重试。
这一条把确定性核验从「类型层」扩展到了「格式层」，
而格式层能挡住相当一部分编造——
模型编订单号时经常编出带字母的。

⚠️ 但 pattern 是双刃剑，实测证实过：
    把设备编号的 pattern 故意写成「4 位数字」（真实值形如 PC-2031）后，
    模型并没有硬填一个违规值，而是直接输出了 null。
    管道没坏——不重试、不崩、不报错，可那个本来就存在、
    而且完全可用的值，被静默丢掉了。
    后果是：该字段变成必填缺失 → 工单掉到红级 → 追问 →
    而顾客已经给过了，问也问不出来。

    所以 pattern 能挡住编造，也能吞掉真实信息，
    两者的表现几乎一样安静。
    加 pattern 之前必须先看一眼真实数据的格式分布；
    宁可少一条校验，也不要用一个想当然的正则。

▍二、日期不得落在未来

未来日期是明显的抽取错误，一次比较即可检出。
这类错误肉眼容易漏，代码一秒钟就能挡。

▍三、依据覆盖率

有依据的字段占非空字段的比例。
它是一个连续量，用于展示「这张工单有多少是可溯的」，
不参与是/否判定。


9.8 三个维度如何合成级别：门槛优先

合成顺序是固定的，因为它们对决策的影响不同：

    第一步  可决策性
        存在阻断级缺陷 → 红，流程结束（其余维度不再定级）

    第二步  忠实性
        存在降级级缺陷 → 黄

    第三步  自洽性
        通用规则命中 → 黄
        提示级标记   → 仅打标，不改变级别

    全部通过 → 绿

为什么自洽性不参与定级：
    三个维度的可计算性不同。
    可决策性与忠实性的大部分子项都能确定性判定，
    而自洽性的业务规则部分算不出来。
    让一个「最不可信」的维度去影响级别结论，
    等于用一个估计去修正两个已知——
    所以它只产生提示，不产生级别。


9.9 依据必须常驻显示，不分等级

由 9.5 的边界可知：忠实性校验会漏掉误读。
而误读是三个维度里最危险的失败——
它让工单看起来完美，却带着错误的结论。

所以有一条硬性展示规则：

    basis（原文依据）必须永远显示，红黄绿一视同仁。

绿色只意味着「不用再追问」，不意味着「不用看依据」。
如果依据只在黄、红时才展开，那误读就永远没人发现。

依据不是降级机制，它是常驻证据。


9.10 提醒要可解释，不要给分数

工单上显示的是「原因」，不是一个分数：

    红 · 信息不全 · 缺 2 项必填：订单号、故障类型
    黄 · 待核实   · 2 个字段无原文依据：影响范围、故障类型
    绿 · 可直接决策 · 缺 1 项选填：照片

理由：伪精确的数字（「68 分」）会让人反复琢磨分数怎么来的，
而「缺哪两项」是能立刻行动的信息。
级别已经是结论，不需要再用一个数字去概括结论。

同时必须配文字标签与图标，不能只靠颜色：
    报告要黑白打印，颜色分级在纸上全部消失；
    色盲用户也读不出来。


9.11 什么算「一张有效的工单」：操作性定义

前九个节说的都是「怎么判断」。但还有一个更根本的问题：
这张工单到底有没有用？

「有效」必须有可操作的定义，否则整件事没法验证。
本设计采用这个标准：

    一张有效工单 =
        人工只看这张工单（不看原始对话），
        在 30 秒内、
        不需要再联系顾客、
        做出一个与「看完原始对话后所作的决策」一致的决策。

三个条件缺一不可，而且每个都能独立测量：

    条件                  指标
    不需要再联系顾客       回问率        ← 主指标
    30 秒内               决策耗时
    与对话后的决策一致     决策一致率

▍为什么主指标是回问率，而不是字段准确率

    因为字段准确率高但决策错，价值等于零。
    而字段有小瑕疵、但只要不用回问顾客，工单就有价值。
    有效性是决策层的性质，不是字段层的性质。

而且回问率有一个额外的好处：
    它可以在生产环境里自动采集。
    工单上有一个「需联系顾客」按钮，
    人工点一下就是一条标签——
    这等于把评测做成了产品埋点，不需要专门的评测活动。

这一点对课程设计尤其重要：
    它让「有效性」从一个一次性实验，
    变成一个可以持续观察的系统指标。


9.12 分级本身如何被验证：只需要单调性

这是最容易被做错的一步。

不要试图证明「85 分 = 90% 正确」——那个证不了（见 9.3）。
要证明的是一个更弱、但足够有用的命题：

    决策一致率（绿） > 决策一致率（黄） > 决策一致率（红）

只要这个顺序成立，分级就有区分度，就有价值。
它是一个相对排序命题，不是绝对估计命题，
因此小样本就能看出趋势。

三种可能出现的结果，对应三种诚实的结论：

    绿高 / 黄中 / 红低      分级有效
    三者接近               分级无效，红黄绿形同虚设
    红不低于黄             门的划分错位，需重定阻断级

后两种是完全可能出现的结果。
如果真的跑出「分级没有区分度」，
正确结论是「当前这套规则不成立」，而不是调参直到它好看。

▍红级要用不同的方法检验

一个反直觉的点：红级的决策一致率低，是设计意图，不是缺陷。
红级本来就不该被用来决策。

所以红级检验的是另一件事：

    它说「缺订单号」，是不是真的缺？

这个可以直接人工核对，成本极低。
于是三个级别有两套检验：

    绿 / 黄  →  测决策一致率（它们承诺「可以决策」）
    红       →  测缺失判定正确率（它承诺「信息确实不全」）

不同级别承诺不同，检验方法也就不同。


9.13 标注数据从哪里来：合成对话

真实对话数据难以获取，但这不影响验证。
自己造对话，造的时候就知道正确答案，而且能控制变量：

    构造类型          用途
    信息完整型        测绿级（应当全对）
    单点缺失型        测追问是否问对了东西
    不可获型          测红级出口（必填项永远拿不到）
    语义模糊型        测忠实性（「试了一下」算不算已穿着）
    情绪干扰型        测误读（「你们这什么质量」）
    多诉求混杂型      测摘要与主诉求识别

其中「情绪干扰型」最值钱：
    它专门打的是忠实性维度的盲区——
    依据校验通过，但值是错的。
    每十条里放两条，看绿级会不会被污染。

这类用例的存在，正是 9.9 那条展示规则的现实依据。


9.14 这一层的实现位置

    纯函数，无外部依赖，不调模型，可完整单元测试：

        QualityEvaluator.evaluate(schema, values, basis, dialogue, now)
            → decision      { blocking[], degrading[] }     可决策性
            → faithfulness  { checkItems[], coverage }       忠实性
            → consistency   { violations[], advisories[] }   自洽性
            → level         红 / 黄 / 绿（按 9.8 的顺序合成）
            → messages      给人看的原因句子列表

    这是整个项目里唯一能写完整单测的核心逻辑，
    也是最值得写干净的一段代码。

    它的输入全是确定性数据（schema / values / basis / dialogue），
    输出全是可枚举的结论，不依赖任何模型调用——
    这保证了对它的测试结果是可复现的。


----------------------------------------------------------------
【十、架构分层与可替换点】
----------------------------------------------------------------

10.1 「打基座」的含义

    基座不是每一层都做完整，
    而是每一层的接口签名定对——
    以后想换掉某个东西，只需要改一个实现。

判断标准：两周之后若要替换某个组件，需要改几个文件？
    ｜
    改 1 个  → 分层成立
    改 20 个 → 没有分层

这套设计里刻意保留的两个可替换点：

    interface LlmClient {
        String chat(List<Message> msgs, Object schema);
    }
        // 换模型（Qwen / GLM / 本地模型）只换实现

    interface Retriever {
        List<String> retrieve(String query);
    }
        // 当前实现：FullInjectRetriever，返回模板 knowledge 全文
        // 将来实现：VectorRetriever，语料变大时接入

这两处之所以值得单独抽象，是因为它们是整套设计里
最可能变化、且变化时最不该牵动业务代码的两块。

10.2 为什么直接调 API，而不是引入 LLM 框架

因为框架封装掉的部分，恰好是本设计要定制的部分：
JSON 校验失败后的重试策略、缺失判定、三维核验与分级、
模板驱动的动态 prompt 拼装。

这些都得绕开框架的抽象自己写。
而裸调一次 HTTP 请求的成本，远低于学习和绕行一个框架的成本。

所以这里的结论是：把抽象做在自己这一层，而不是引入别人的抽象。
一个几十行的 LlmClient 接口，比引入整套框架更接近「基座」。

10.3 技术选型的原则

选型只跟一个标准走：它对「对话 → 结构化 → 工单」这条主链路
有没有直接贡献。有则加，无则不加。

这条原则的直接后果：
    加：确定性的字段校验（可靠性）、接口文档（两人协作的契约）
    不加：向量数据库、embedding、对象存储、消息队列、
          缓存中间件、容器化、富文本编辑器
          —— 它们服务的是别的问题，不是这套设计的核心矛盾。

后来去掉的一项：流式输出。
    在「AI 回答商品问题」的形态下它是必要的，
    定位收敛为「抽取 + 追问」之后它失去了服务对象：
    端到端延迟约 1 秒，输出是结构化 JSON，
    而顾客看到的两句话都由代码瞬时拼装。
    这是一个随定位变化被推翻的早期决定——
    选型原则本身没错，是它服务的形态变了。

一个通用系统的诱惑，永远是「顺便也支持一下」。
而「顺便」是设计里最贵的一个词。


----------------------------------------------------------------
【十一、非目标（刻意不做）】
----------------------------------------------------------------

明确写下不做什么，是这套设计的一部分，而不是附注。

▍字段类型：只支持 6 种，且不再扩张

    text     自由文本
    enum     单选枚举        ← 决策主力，AI 只能取给定值之一
    number   数值
    boolean  布尔
    date     日期（相对时间需换算）
    image    图片

关于 image：本期 AI 不处理图片。
    规则：遇到 image 字段一律填 null，由核验层按必填/选填处理，
    并提示顾客上传，图片由人工在工单里补。

    这个决定同时解决两个问题：
        技术上完全避开多模态；
        逻辑上图片证据本来就应该由人看。

类型系统一旦放开就是无底洞：
每增加一个类型，等于前端控件 + prompt 指令 + 校验规则 + 抽取调试。
所以「支持 6 种并把它们做对」比「支持 20 种」更符合设计意图。

▍不做流程编排

    只做固定状态机，不做审批流画布 / BPMN。

    理由：这套设计的产出物是「一个可决策的结构化工单」，
    到这里价值已经交付完毕。工单之后怎么流转，
    属于另一个问题域（工作流引擎），把它卷进来
    会稀释核心，而不会增强核心。

    「只提供工单」这个边界，是这套设计的锋利之处，不是它的缺陷。

▍不做拖拽式表单设计器

    不做布局、分栏、条件显示、字段联动、字段级权限。

    理由见 5.3：这些属于「表单设计器」，
    与「对话 → 结构化」的核心价值无关。

▍不做可配置的评分权重

    评分规则写死在代码里，不开放给模板作者调。

    理由：让用户调权重，等于让用户定义「什么算好工单」，
    而这恰恰是最容易陷入主观争执、却带来不了实际价值的地方。
    固定规则更容易解释，也更容易答辩。

▍不做与主链路无关的常规设施

    登录 / 权限、分页、搜索、导出、多语言、容器化、中间件。

    它们在任何系统里都需要，但不承载这套设计的思想。
    在有限的篇幅里，它们的成本会挤掉真正需要打磨的部分。


----------------------------------------------------------------
【十二、设计主张（一句话各一条）】
----------------------------------------------------------------

1. AI 的产出物必须从文本变成结构化数据。
   只有结构化，才可校验、可测试、可流转、可版本化。

2. 业务知识归领域用户，不归开发者。
   字段定义权与知识块的归属，是这套设计的支点。

3. 字段从决策倒推，不从对话里抽。
   必要性治缺失（并决定必填还是选填），敏感性治冗余，
   可获性连接对话能力。

4. 模型只回答「看到了什么」，代码只回答「够不够」。
   让模型同时抽取和审计自己，它的评价会污染它的抽取。

5. 把「置信度」切成三个维度：完备性→可决策性、忠实性、自洽性。
   一个数字同时表达三件事，是这套设计里所有困惑的来源。

6. 完备性不能删。
   它一半服务于可决策性（重叠），
   另一半用于检验模板本身合不合理（不冲突）。

7. 度量用比率，判定用否决。
   比率衡量趋势，否决下结论；两者混成一个数，
   会同时失去可读的趋势和清晰的边界。

8. 可决策性用否决，忠实性用逼近，自洽性只用提示。
   三者的可计算性不同，就不该用同一种方式合成。

9. 不给概率，只给结论。
   算得出缺陷，算不出概率；级别与严重度分开，
   不合成任何伪造精度的分数。

10. 分级的作用是提醒真实的人，不是给 AI 打分。
    所以颜色绑定的是「能不能点决策按钮」，
    显示的必须是「缺哪几项」，而不是一个分数。

11. 缺失与依据都必须常驻可见。
    basis 永远显示，绿黄红一视同仁——
    因为绿色只保证信息齐全，不保证判断正确；
    空缺会被发现，错误不会被发现。

12. 有效性定义在决策层，不在字段层。
    主指标是「人工是否还得回去问顾客」，
    它可以在生产环境用一次点击采集。

13. 允许字段可变，就必须接管字段的演化史。
    schema 版本化是「自由设计」这个承诺的前提，不是附加项。

14. 通用性来自管道与模板的解耦，不来自功能数量。
    「顺便也支持一下」是设计里最贵的词。
