# 模块划分

> 本文说明**系统代码**怎么划分模块，供阅读代码、二次开发和评审使用。
> 测试用例按功能分成 A–O 模块（定义在 qa/build-testcases.py，执行表是 [测试用例-手工执行版.xlsx](测试用例-手工执行版.xlsx)），
> 与本文的代码模块是两套视角，两者的对应关系见第八节。

## 一、总体架构

系统是一个前后端分离的 Web 应用，后端按**分层**划分，前端按**两个端**划分。

```
┌─────────────────────────── 浏览器 ───────────────────────────┐
│  采购录入端 /            │        台账管理端 /admin/          │
│  记一笔 · 手填 · 我的记录  │  台账 · 详情审核 · 供应商 · 统计   │
│        (Vue 3 单页)      │        (Vue 3 + 路由 hash)        │
└───────────┬───────────────────────────┬─────────────────────┘
            │        HTTP / JSON        │
            │  统一响应 { code, message, data }                │
┌───────────┴───────────────────────────┴─────────────────────┐
│                        后端 (Spring Boot)                    │
│                                                              │
│  接入层   AuthInterceptor · GlobalExceptionHandler           │
│  接口层   *Controller（8 个，共 29 个接口）                   │
│  应用层   EntryService · LedgerService · SupplierService     │
│           StatsService · LedgerExportService                 │
│  领域层   ComplianceEvaluator · LedgerStatus · TemplateSchema│
│           LedgerValueMapper · FollowUpBuilder · PromptBuilder│
│  基础层   LlmClient · UploadController · Mybatis-Plus Mapper │
└───────────────────────────┬─────────────────────────────────┘
                            │
                    MySQL 8 · food_ledger（7 张表）
                    uploads/ 目录（索证索票照片）
```

**一句话概括分层意图**：接口层只做参数与权限，应用层编排流程，
**判定规则放在领域层且不依赖 Spring**（`ComplianceEvaluator` 可直接单测），
外部依赖（模型、文件、数据库）都在基础层收口。

## 二、后端模块清单

13 个包，共 64 个类（约 4500 行）。按职责分四组：

### 2.1 基础层

| 包 | 职责 | 关键类 | 说明 |
|---|---|---|---|
| `common` | 公共契约 | `ApiResponse` `BizException` `GlobalExceptionHandler` `PageResult` `Attachment` | 统一响应体、业务异常、分页结果、附件结构。**不含任何业务逻辑** |
| `config` | 框架配置 | `MybatisPlusConfig` `WebConfig` | 分页插件、乐观锁插件、静态资源映射（`/uploads/**`） |

### 2.2 身份与主数据层

| 包 | 职责 | 关键类 | 说明 |
|---|---|---|---|
| `auth` | 登录、会话、权限 | `AuthController` `AuthService` `AuthInterceptor` `CurrentStaff` `StaffView` | Cookie 会话（非 JWT）、BCrypt 校验、拦截 `/api/**`；角色 `PURCHASER` / `MANAGER` |
| `staff` | 人员数据 | `Staff` `StaffMapper` `StaffSeeder` | 首次启动自动建两个演示账号（密码哈希不写死在 SQL 里） |
| `template` | 台账模板与字段定义 | `TemplateSchema` `TemplateField` `TemplateService` `TemplateController` | **字段的唯一来源**：法定 12 项 + 自定义 9 项，前端表单与 AI 提示词都由它驱动 |
| `category` | 品类主数据 | `Category` `CategoryMapper` `CategoryController` | 8 个品类；录入时按名称解析成 `category_id` |
| `supplier` | 供应商与证照 | `SupplierService` `SupplierController` `SupplierView` | 证照到期天数计算与预警（30 天内 / 已过期） |

### 2.3 核心业务层

| 包 | 职责 | 关键类 | 规模 |
|---|---|---|---|
| `record` | **台账的完整生命周期**：录入、判定、状态流转、查询、值映射 | `LedgerService`（570 行）`ComplianceEvaluator`（158 行）`LedgerStatus` `QualityLevel` `LedgerValues` `LedgerValueMapper` `LedgerController` | 14 个类 |

`record` 里再分四块，读代码时按这个顺序看：

| 子块 | 类 | 做什么 |
|---|---|---|
| 数据 | `LedgerRecord` `LedgerRecordMapper` | 一张表一行一个品项；法定项目建列，自定义字段进 `extra_json` |
| 判定 | `ComplianceEvaluator` `LedgerQuality` `QualityLevel` | 红/黄/绿三级：缺法定 → 红（不能入账）；缺选填 → 黄（可入账）；齐 → 绿。**纯函数，构造时传模板，不碰数据库** |
| 状态 | `LedgerStatus` | 状态机：待入账 → 已入账 / 退回补录 / 已作废；退回补录 → 待入账 |
| 映射 | `LedgerValues` `LedgerValueMapper` | 记录 ↔ 值表（key 就是模板字段 key）；品类名 → id；附件 JSON ↔ List |

### 2.4 应用编排层

| 包 | 职责 | 关键类 | 说明 |
|---|---|---|---|
| `entry` | **AI 录入的编排**：会话、对话、追问、确认、落库 | `EntryService`（276 行）`EntryStore` `Extractor` `PromptBuilder` `FollowUpBuilder` `EntryController` | 只负责"把一句话变成一张值表"，落库仍调 `LedgerService` |
| `llm` | 模型客户端 | `LlmClient` | 仅这一处出现 HTTP 调模型；`response_format=json_object`、temperature 0 |

### 2.5 输出层

| 包 | 职责 | 关键类 | 说明 |
|---|---|---|---|
| `stats` | 统计聚合 | `StatsService` `StatsOverview` `StatsController` | 在 Java 里聚合（不是 SQL GROUP BY）；总金额排除已作废；已入账金额与总金额分列 |
| `export` | Excel 导出 | `LedgerExportService` | 复用列表的筛选条件；标题行 + 条件行 + 表头冻结 + 23 列；级别用中文文本便于黑白打印 |
| `upload` | 附件上传 | `UploadController` | 扩展名白名单、10MB 上限、服务端生成 UUID 文件名、按年月存放 |

## 三、前端模块划分

一套依赖，两个入口（MPA）：

| 位置 | 职责 | 文件 |
|---|---|---|
| `shared/api` | 请求层 | `http.js`（统一解包 `{code,message,data}`、401 整页跳登录）、`auth/entry/ledger/template/upload.js`（按域分包） |
| `shared/components` | 可复用组件 | `LedgerForm.vue`（**按模板渲染表单**，手填与补录共用）、`GradeTag.vue`（级别标签）、`LoginCard.vue`（两端共用的登录卡片） |
| `shared/draft.js` | 草稿暂存 | 按用户存 `sessionStorage`，切页签/刷新不丢，退出登录清除 |
| `user/*` | 采购录入端 | `App.vue`（三页签 + 角色分流）、`EntryView`（AI 对话）、`ManualEntryView`（手填）、`MyRecordsView`（我的记录 + 补录抽屉） |
| `admin/*` | 台账管理端 | `router`（hash 路由 + 守卫）、`authStore`（登录态缓存）、`LedgerListView`（筛选/分页/导出）、`LedgerDetailView`（审核动作）、`SupplierListView`、`StatsView` |

**前端唯一的架构约定**：**表单字段一律来自 `/api/templates/default`，前端不写死字段清单。**
这条约定是被真实缺陷换来的——补录页曾写死 17 个字段，导致"产地/冷链温度/农残报告"
在界面上根本没有输入框，采购员永远补不到"记录完整"。

## 四、模块依赖关系

依赖方向**单向向下**，不允许反向或循环：

```
Controller → Service ─┬→ 领域类（Evaluator / Status / ValueMapper）
                      ├→ Mapper（数据库）
                      └→ 其它 Service（仅两类：entry→record，stats/export→record）
```

| 模块 | 依赖 | 明确**不**依赖 |
|---|---|---|
| `auth` | `staff` | 台账（不碰业务数据） |
| `template` | — | 台账（模板不知道谁在用） |
| `record` | `template` `category` `common` | `entry` `llm`（核心域不认识 AI） |
| `entry` | `record` `template` `llm` | `stats` `export` |
| `stats` `export` | `record` `template` | `entry` `llm` |
| `upload` | `common` | 任何业务表 |

**这条"核心域不认识 AI"是故意的**：`LedgerService.create` 不需要知道记录是 AI 录的还是人手填的，
两条路只在映射器（`LedgerValueMapper`）汇合。若反过来让 `record` 依赖 `entry`，
"手填"就会变成 AI 的附属品，而实际上手填是一等公民。

## 五、数据模型与模块归属

7 张表，每张表只归一个模块写：

| 表 | 归属模块 | 存什么 |
|---|---|---|
| `staff` | `staff` | 人员与 BCrypt 密码、角色 |
| `supplier` | `supplier` | 供应商主数据 + 证照号与到期日 |
| `ingredient_category` | `category` | 品类主数据（8 项） |
| `ledger_template` | `template` | 模板与 `fields` JSON；记录里另存 `schema_snapshot` 保证历史判定不变 |
| `ledger_record` | `record` | 台账主表，45 列：法定项目 + 判定结果 + 溯源（`basis` / `source_type` / `session_id`）+ 乐观锁（`version`）+ 修订号 |
| `entry_session` | `entry` | 一次录入会话：状态、已抽到的值、追问次数、生成的记录号 |
| `entry_message` | `entry` | 对话消息（原文留存，用于"依据"回溯） |

## 六、五条关键设计约束

这几条决定了模块边界，改动时不要绕开：

1. **法定项目建列，自定义字段进 `extra_json`**
   《食品安全法》第五十三条把 12 项进货查验项目写死了 —— 法律固定 = schema 固定。
   只有建列才谈得上按日期筛、按供应商汇总、按批号追溯、导出 Excel。

2. **判定在代码里，不交给模型**
   `ComplianceEvaluator` 是纯函数，同一笔采购不能两次判出两个级别。
   模型只负责"抽值"，级别由代码算。

3. **AI 只能产出「待入账」记录**
   `EntryService` 从不调用 `post`。入账必须由管理员在管理端点，且红色记录点不动。

4. **模板是字段的唯一来源**
   前端表单、AI 提示词、补录界面、Excel 导出列都用同一份模板。
   历史上出现过三次"有列但不在模板里"的缺陷（到期日、附件、品类），都是同一个根因。

5. **台账不物理删除**
   只有「作废 + 原因」。状态机里没有删除边，接口里没有 DELETE。

## 八、与测试模块的对应

测试用例把功能按**用户能看到的功能区块**分成 A–O 共 15 个模块；本文按**代码**分。
两者对照（改代码后可以据此挑要回归的用例）：

| 代码模块 | 对应测试模块 |
|---|---|
| `auth` `staff` | A 登录与权限 |
| `entry` `llm` | B 录入端 · AI 记一笔 |
| `record`（录入路径）`template` | C 录入端 · 手填 |
| `record`（查询路径） | D 我的记录与补录、E 台账列表 |
| `record`（状态机） | F 详情与审核 |
| `supplier` | G 供应商与证照 |
| `stats` | H 统计 |
| `export` `upload` | I 导出与附件 |
| —（无对应代码） | J 异常与边界 |
| 跨模块 | K 端到端场景 |
| `entry` `llm` + `record`（查询） | L 提示词攻击、M SQL 注入 |
| 全部 | N 本轮反馈复测、O 安装与部署 |

## 九、扩展点：三类改动各要动哪里

**加一个自定义字段**（如"检疫证编号2"）：
1. `db/data.sql` 与 `ledger_template.fields` 追加字段定义（模板版本 +1）
2. 前端无需改动（表单按模板渲染）
3. 若该字段需要参与合规判定：标 `required: true`，判定代码无需改
4. 若需单独建列（要能筛选/统计）：改 `schema.sql`、`LedgerRecord`、`LedgerValues.of`、`LedgerValueMapper`
   —— **注意这是四处，漏一处就是"有列但录不进去"**

**加一个品类**：`ingredient_category` 插一行即可；`category_id` 与筛选自动生效。
**加一种录入方式**（如扫码）：新建应用层模块，产出"值表"后调 `LedgerService.create`，
不要绕过映射器与判定。

## 十、已知的模块设计问题

诚实记录，给后续重构留线索：

| 问题 | 影响 | 建议 |
|---|---|---|
| `LedgerService` 570 行，包含查询、状态流转、判定调用、值转换 | 改动集中、难复用 | 拆成 `LedgerCommandService`（写：录入/流转）与 `LedgerQueryService`（读：筛选/分页） |
| `record` 与 `template` 双向概念耦合（模板驱动判定、判定结果写回记录） | 模板改版要考虑历史快照 | 已有 `schema_snapshot` 缓解，保持"记录只认自己的快照"这条 |
| `stats` 在内存聚合 | 数据量上万后变慢 | 改 SQL 聚合，接口形状不变 |
| 附件公开可读 | 凭证照片无鉴权 | 改签名 URL 或加拦截 |
| 业务错误统一 HTTP 200 + `body.code` | 与 REST 惯例不一致，网关/浏览器识别不到 | 单独一轮改造，同时调整前端与 62 条回归 |
