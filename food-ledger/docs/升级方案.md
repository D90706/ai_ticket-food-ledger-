# 升级方案 v2：从课程设计到可交付系统

> 课程设计阶段的目标是"跑通并证明思路"；升级阶段的目标是"敢交给一个真实食堂用"。
> 本文件汇总升级方向、依据（实测数据）、验收标准与路线图，供后续迭代与评审使用。

## 一、为什么现在升级

先做了一次体检（2026-10-30 实测），结论是：

**系统现在能保证"记录完整"，但不能保证"记录可信"。**

| 检查项 | 实测现状 | 意味着什么 |
|---|---|---|
| 数据表约束 | `ledger_record` 上**只有主键**，0 个 CHECK、0 个外键、0 个唯一键 | 数据库不是最后一道防线，全靠应用层 |
| 12 项法定列 | **11 项允许 NULL**（只有 `ingredient_name` 非空） | 缺项只能靠判定拦，DB 层不拦 |
| `supplier_id` | **55 / 55 条为空** | 供应商模块与台账没真正关联；"供应商金额 Top"靠名称字符串聚合，改一个字就断 |
| 金额自洽 | **2 条** 金额 ≠ 数量 × 单价 | 红黄绿只算完备性，**抓不到这类错** |
| 测试覆盖 | 133 条手工用例 / 62 条接口回归 / 20 条界面点击 / 12 条单测 | 覆盖"功能是否可用"，没覆盖"数据是否正确" |
| AI 抽取评测 | 16 条用例：准确 100%、召回 100%、瞎填 0%、依据编造 3.7% | 样本小且与提示词同源，只能说明"在这 16 条上成立" |

一句话：**红黄绿衡量的是「字段齐不齐」，而真实风险在「值对不对」。**

## 二、升级的四个方向

```
可信性  ──▶  U1 一致性复核层（代码优先，模型其次）
结构保障 ──▶  U2 数据库约束（约束跟着状态走）
主数据  ──▶  U3 供应商真正关联
人机分工 ──▶  U4 agent 取料、人做决策
对外能力 ──▶  U5 A2A 就绪（设计现在做，协议接入后面再说）
```

## 三、U1 一致性复核层

### 问题
现有三级只是**完备性**：缺法定→红、缺选填→黄、齐→绿。
但"齐但错"的情况全部漏过——数量错一个量级、金额手填不符、供货者名字错、凭证号编的，都会判成绿色。

### 方案：三态结论，不是置信度分数

模型自评的"置信度 0.87"**不可校准**，且一旦显示出来就会被当依据。改成可反驳的具体发现：

```
复核结论：REVIEW（1 处待确认）
  ✓ 金额 294.00 = 数量 12 × 单价 24.5
  ✓ 生产日期 2026-10-26 ≤ 进货日期 2026-10-28
  ! 供货者「城南肉联厂」未在供应商主数据登记（最接近：城南肉联厂）
```

三层职责分开，不要都交给模型：

| 层 | 谁做 | 检查内容 | 成本 | 优先级 |
|---|---|---|---|---|
| **L1 确定性** | 代码 | 见下方 8 条规则 | 零 | **先做** |
| **L2 依据复核** | 模型 | 每个值能否由 `basis` 那句原文推出（验证比生成容易） | 1 次调用/条 | 第二 |
| **L3 取证** | OCR+模型 | 凭证照片上的证号 vs 填的证号 | 需 OCR | 后做 |

**L1 的 8 条规则**（全部可代码实现）：

| # | 规则 | 判定 |
|---|---|---|
| 1 | 算术 | `数量 × 单价 = 金额`（容差 0.01） |
| 2 | 日期顺序 | 生产日期 ≤ 进货日期 ≤ 今天；到期日 > 生产日期 |
| 3 | 保质期推算 | 到期日 ≈ 生产日期 + 保质期（按天/月解析，容差 2 天） |
| 4 | 主数据 | 供货者名称模糊匹配 `supplier` 表 |
| 5 | 唯一性 | 同批号 + 同供货者是否已存在（防重复录入） |
| 6 | 价格离群 | 单价 vs 该品名历史中位数（2 倍外报警） |
| 7 | 单位常识 | 数量与单位不匹配（如 2000 斤鸡蛋） |
| 8 | 占位词 | 值里出现"未知/不详/待补/无"（等价于没填） |

### 验收标准（必须先有评测集）
构造 **8 类错误 × 5-10 条** = 40-80 条"齐但错"记录：

```
数量错一个量级 / 单价小数点错位 / 金额手填不符
生产日期错年 / 到期日早于生产 / 进货日期在未来
供货者名称错字 / 品名与品类矛盾
```

| 指标 | 目标 |
|---|---|
| 召回率（真错的被抓到） | **≥ 80%** |
| 误报率（对的被误标） | **≤ 20%** |
| 人工核减比例 | 记录（人只需看 REVIEW/SUSPECT） |

> **误报率是生死线**：超过 30%，人工会开始无视所有提示，这一层等于没做。

### 风险
- **只做加法**：复核结论不能把记录变成"免检"，红黄绿照旧并列显示
- **失败不阻塞**：复核超时或模型挂了 → 记为"未复核"，流程照走
- **必须抽样反查**：对复核 PASS 的绿色记录人工随机抽 10% 全检，用来持续校准

## 四、U2 数据库约束：约束要跟着状态走

### 关键决策：**不做 NOT NULL**
把 12 项法定列改成非空会直接毁掉红黄绿——红黄的定义就是"缺项"，一旦非空，系统只能逼人填假值。

### 方案：条件 CHECK（引用同行的 `status`）

```sql
ALTER TABLE ledger_record
  -- ① 只有「已入账」才要求法定项齐全
  ADD CONSTRAINT ck_posted_complete CHECK (
    status <> 'POSTED' OR (
      spec IS NOT NULL AND quantity IS NOT NULL AND unit IS NOT NULL
      AND production_date IS NOT NULL AND batch_no IS NOT NULL
      AND shelf_life IS NOT NULL AND purchase_date IS NOT NULL
      AND supplier_name IS NOT NULL AND supplier_address IS NOT NULL
      AND supplier_phone IS NOT NULL AND certificate IS NOT NULL)
  ),
  -- ② 作废必须有原因
  ADD CONSTRAINT ck_void_reason CHECK (
    status <> 'VOID' OR (void_reason IS NOT NULL AND TRIM(void_reason) <> '')
  ),
  -- ③ 算术自洽
  ADD CONSTRAINT ck_amount_math CHECK (
    amount IS NULL OR unit_price IS NULL OR quantity IS NULL
    OR ABS(amount - unit_price * quantity) < 0.01
  ),
  -- ④ 日期逻辑
  ADD CONSTRAINT ck_date_order CHECK (
    (production_date IS NULL OR purchase_date IS NULL OR purchase_date >= production_date)
    AND (production_date IS NULL OR expiry_date IS NULL OR expiry_date > production_date)
  ),
  -- ⑤ 数量为正
  ADD CONSTRAINT ck_qty_positive CHECK (quantity IS NULL OR quantity > 0),
  -- ⑥ 状态枚举
  ADD CONSTRAINT ck_status_enum CHECK (status IN ('PENDING','POSTED','RETURNED','VOID'));

-- ⑦ 外键（先回填 supplier_id）
ALTER TABLE ledger_record
  ADD CONSTRAINT fk_record_supplier FOREIGN KEY (supplier_id) REFERENCES supplier(id);
```

### 三个必须先处理的事
1. **清数据**：现有 2 条金额不符、55 条 `supplier_id` 为空 —— 不先修，`ALTER` 直接失败
2. **状态转换合法性 DB 表达不了**（CHECK 看不到旧行）→ 继续留在应用层的 `LedgerStatus`
3. **异常要翻译**：约束触发抛 SQL 异常，需在 `GlobalExceptionHandler` 转成中文 400

## 五、U3 供应商主数据真正关联

| 项 | 现状 | 目标准则 |
|---|---|---|
| `supplier_id` | 55/55 为空 | 新记录 100% 非空 |
| 名称匹配 | 无 | 录入时按名称模糊匹配主数据；未匹配走"确认/新建" |
| 统计口径 | 按 `supplier_name` 字符串聚合 | 改按 `supplier_id` 聚合 |
| 约束 | 无外键 | `fk_record_supplier` |

## 六、U4 人机分工：agent 取料，人做决策

### 分工重排

| 工单状态 | 问题性质 | 谁处理 | 人工投入 |
|---|---|---|---|
| 红色（缺法定） | **补料** | agent 追问 / 从凭证 OCR 取 / 退回 | 不用逐条看 |
| 黄色（缺选填） | **补料** | 同上（也可直接入账） | 不用 |
| 绿色（齐全） | **决策** | 人工 + 复核结论辅助 + 抽查 10% | 集中在这里 |

### 两条禁令（否则风险反向放大）
1. **agent 不得"补"缺失值**。只允许三种动作：追问、OCR 取得、生成"要补什么+为什么"清单。
   一旦允许"看着差不多就补上"，红黄会被洗成绿色直接进人工——**这是最危险的失败模式**，而且看起来像"系统变聪明了"。
2. **不得把复核 PASS 当免检**。人看到的必须是"结论 + 引用"，不是"字段齐了"，且必须保留抽样。

### 双 agent 的独立性
同模型、同输入的两个 agent，错误高度相关，"两票通过"几乎不提供额外保证。要真独立：

| | 生成 agent | 复核 agent |
|---|---|---|
| 输入 | 采购员那句话（对话） | 依据原文 + 主数据 + 凭证 + 同批号历史 + 价格统计 |
| 任务 | 从零生成值 | 判断值是否成立 |
| 机制 | 模型 | L1 代码 + L2 模型（不同机制） |

### 验收标准
- 单条记录的人工审核时长下降 ≥ 50%（改造前后各计 20 条的均值）
- 抽样反查的差错率 ≤ 2%

## 七、U5 对外能力：A2A 就绪（现在不接协议）

现有会话结构天然对得上 A2A 的任务生命周期：

| 现有概念 | A2A 对应 |
|---|---|
| 建会话 | Task 创建（contextId） |
| `replyType = ASK` / 确认卡 | `INPUT_REQUIRED` |
| 生成记录 | `WORKING → COMPLETED` |
| `recordId + 级别 + 缺失项` | `Artifact` |
| 上传凭证照片 | Message 的 parts |

**决策：进程内实现，不引入 A2A 协议。** 只在需要被别的系统（集团采购平台、财务）调用时，才暴露 `/.well-known/agent-card.json`。

要补的四个缺口：

| 缺口 | 为什么 |
|---|---|
| 幂等键 | A2A 要求接收方假设重复投递；现在重复提交会生成两条记录 |
| agent 认证 | 现在是 cookie session，agent 调不了；要发可撤销的 Bearer token |
| 异步任务模型 | 现有接口全同步；长任务需要 `returnImmediately` + 轮询 |
| 入站防注入 | agent 来的消息同样不可信，复用现有 `qa/probe-attacks.py` 思路 |

## 八、顺带清掉的技术债

| # | 问题 | 影响 | 动作 |
|---|---|---|---|
| 1 | `LedgerService` 570 行，读写混在一起 | 改动集中、难复用 | 拆 Command / Query |
| 2 | 统计在 Java 内存聚合 | 上万行变慢 | 改 SQL 聚合，接口形状不变 |
| 3 | 附件公开可读，无鉴权 | 凭证照片可被猜路径访问 | 签名 URL 或加拦截 |
| 4 | 业务错误统一 HTTP 200 + `body.code` | 网关/浏览器识别不到 401 | 单独一轮改造，同步改前端与 62 条回归 |
| 5 | 单一模板 | 多品类多字段做不到 | 模板列表 + 按品类启用 |
| 6 | 无「不适用」标记 | 鸡肉没农残报告 → 永远停在待补证，够不到绿色 | 字段级 `不适用`，判定跳过 |
| 7 | 历史数据无品类 | 品类筛选漏老数据 | 按品名批量预填 + 人工复核 |
| 8 | 无 `voided_by` / `voided_at` | 靠 `last_actor`/`updated_at` 推断 | 补两列（做"撤销作废"前必须补） |
| 9 | 评测不进 CI | 抽取质量会悄悄退化 | `RUN_EVAL=1` 纳入流水线 |

## 九、路线图

| 阶段 | 内容 | 工期 | 可验收的数字 |
|---|---|---|---|
| **P0 结构保障** | 清数据 + 6 条 CHECK + 回填 `supplier_id` + 外键 | 1–2 天 | DB 拒写非法数据；`supplier_id` 非空率 100% |
| **P1 复核层 L1** | 8 条规则 + `ai_review` 表 + 造评测集 | 3–5 天 | L1 召回 ≥ 80%、误报 ≤ 20% |
| **P2 复核层 L2** | 值↔依据模型复核 + 详情页"复核"区块 + 列表"待复核"筛选 | 3–5 天 | 增量召回；单条审核时长 −50% |
| **P3 取证与技术债** | 凭证 OCR + 技术债 1/2/6/9 | 1–2 周 | 红黄自动补全率；统计改 SQL 后响应时间 |

**P0 先做的理由**：零模型成本、不依赖任何讨论结论、且现在就能抓到那 2 条错记录。

## 十、明确不做

- 不做多租户 / 多食堂
- 不做采购下单、库存扣减、财务对账
- 不训练自己的模型
- 不接入 A2A 协议（只保留接口形状）
- 不做移动端适配

## 十一、"升级完成"的判据

全部满足才算完成：

1. `ledger_record` 上有 6 条 CHECK + 1 个外键，且 DB 能拒绝非法写入
2. 新记录 `supplier_id` 非空率 100%，统计按 id 聚合
3. 存在 ≥ 40 条"齐但错"评测集，L1+L2 召回 ≥ 80%、误报 ≤ 20%
4. 单条记录人工审核时长下降 ≥ 50%（同口径前后对比）
5. 绿色记录中有复核标记的比例、以及被抽样的比例，可查可报
6. 技术债 1/2/3/6 已关闭
