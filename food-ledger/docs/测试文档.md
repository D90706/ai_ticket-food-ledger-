## 一、文档说明

本文档用于线下测试人员执行手工测试，包含测试模块划分、全部用例的步骤与预期结果、缺陷记录，以及执行与记录方式。

工程里四份文档分工不同，不要混用：

| 文件 | 作用 | 谁维护 |
|---|---|---|
| `docs/测试文档.docx` | 打印与提交用的正式文档 | 测试负责人 |
| `docs/测试文档.md`（本文件） | 工程内可读、可 diff 的同一份内容 | 测试负责人 |
| `docs/测试用例-手工执行版.xlsx` | 执行记录：逐条勾结论、登记缺陷编号与执行人 | 执行测试的人 |
| `docs/test-plan.md` | 开发侧接口回归的模块划分与缺陷复盘（偏技术） | 开发 |
| `docs/eval-report.md` | AI 抽取准确率的定量评测与局限说明 | 开发 |

**为什么定义与执行要分开**：用例是「定义」，同一套用例会被执行多轮（每轮修复后回归）。把结果写在用例旁边，第二轮就没法在同一份文件里复用；分开之后执行表可以按轮次另存。

## 二、被测系统与测试范围

### 2.1 系统构成

系统分两个端，同一套后端：

- **采购录入端** `http://localhost:5174/`：一句话录入（AI）、手填、我的记录与补录。给采购员用。
- **台账管理端** `http://localhost:5174/admin/`：台账列表、审核入账、退回补录、作废、供应商与证照、统计、导出。给管理员用。
- **后端** `http://localhost:8081`：接口、合规判定、AI 抽取、Excel 导出、附件存储。
- **数据库** MySQL 8，库名 `food_ledger`，7 张表。

### 2.2 本轮测什么

重点是「一笔采购能不能被完整、可追溯地记下来，并且能被审核与检查」：

- **录入**：AI 对话录入与手工表单录入两条路都要能走通，且合规判定一致。
- **判定**：法定项目缺失必须拦住入账；临期与过期要给出提示。
- **流转**：待入账 → 入账 / 退回补录 / 作废；退回后补录要能回到待审核。
- **查证**：按日期、供货者、品类、状态、级别、批号都能查；导出可用于检查。
- **安全**：AI 入口不被提示词操纵；查询不被注入。

### 2.3 本轮不测什么

明确不测，避免把时间花在边界外，也避免交付时对「测没测」产生分歧：

- 并发压测：只做两人手工同时保存，不测百人同时操作。
- 模型抽取准确率：有独立评测报告（`docs/eval-report.md`），不在手工用例里重复。
- 浏览器兼容性：只保证 Chromium 内核（Edge/Chrome）。
- 权限细分：只有采购员/管理员两种角色，没有按品类或金额分级授权。
- 数据迁移：不测从旧系统导入台账。

### 3.2 首次安装（含建库建表）

两条命令缺一不可。第二条必须用参数指定库名——种子文件里没有 `USE` 语句：

```bash
cd food-ledger
mysql -u root -p < src/main/resources/db/schema.sql
mysql -u root -p food_ledger < src/main/resources/db/data.sql
mvn spring-boot:run                      # 后端 8081
cd web && npm install && npm run dev     # 前端 5174
```

> ⚠️ `schema.sql` 是重建式的（先 `DROP TABLE` 再 `CREATE`），只在开发期使用；库里已有台账数据时不要执行，会清空。演示账号由程序首次启动时自动创建，不需要手工插用户。

### 3.4 数据准备与清理

部分模块依赖既有数据，开始前先看这张表，避免「筛不出来」被误当成缺陷：

| 模块 | 需要什么数据 | 怎么造 |
|---|---|---|
| E 台账列表 | 红/黄/绿三种级别、四种状态（待入账/已入账/退回补录/已作废）、临期与已过期各有若干条 | 用 C 模块「只填名称」造红级；手填完整造绿级；把到期日改成昨天造过期 |
| F 详情与审核 | 至少一条可入账的、一条不合规的、一条已入账的 | 同一条记录依次走：入账、退回、作废 |
| G 供应商 | 无（新增即可） | 新增时把许可证到期日设为今天+12 天和昨天各一个 |
| H 统计 | 有已作废记录、有跨月数据 | 作废一条；把某条记录的进货日期改到上个月 |
| K 端到端 | 两个浏览器窗口，分别登录两种账号 | 一个普通窗口，一个无痕窗口 |

**清理**：台账不支持物理删除，测试数据由管理员「作废」并写明原因。不要用 SQL 直接删表或删行——会破坏统计口径与可追溯性，也会让后续测试的基准数据对不上。

## 五、优先级、判定标准与缺陷分级

### 5.1 用例优先级

| 优先级 | 含义 | 对交付的影响 |
|---|---|---|
| P0 必测 | 主干功能：不通过就无法交付 | 任一 P0 不通过，本轮判定为不通过 |
| P1 应测 | 重要功能：异常会影响使用，但有替代路径 | 允许带缺陷交付，但必须登记并在下轮修复 |
| P2 可选 | 体验与边界：时间允许时执行 | 不阻塞交付 |

### 5.2 通过判定

- **单条用例**：实际结果与「预期结果」一致记为通过；不一致记为不通过，并在缺陷记录页登记。
- **模块**：该模块 P0 全部通过，且不通过项已登记缺陷，记为模块通过。
- **本轮**：所有 P0 通过记为通过；任一 P0 不通过记为不通过。
- **阻塞**：服务起不来、页面白屏等，记为「阻塞」，暂停该模块，先测其它模块，不要空等。

### 5.3 缺陷严重级别

| 级别 | 判定标准 | 本项目中的例子 |
|---|---|---|
| 致命 | 台账数据丢失或错乱、越权能看到别人数据、无法入账 | 改一个字段把其余法定项目清空（D-01） |
| 严重 | 主干功能不可用，且没有替代路径 | 附件挂不到台账上（D-03）；补录后状态不回流（D-08） |
| 一般 | 功能可用但结果不对 | 品类筛不出鸡肉（D-04）；图片显示不出来（D-07） |
| 轻微 | 提示文案错误、样式错位、非关键字段显示异常 | 角色提示条文案不通顺 |
| 建议 | 可用性改进，不阻塞交付 | 筛选加实时刷新（D-06） |

## 七、执行与记录方式

### 7.1 执行顺序

建议 A → B → C → D → E → F → G → H → I → J → L → M → O → N → K。N（本轮反馈复测）放在 O 之后，因为它是前一轮问题的验证；K（端到端）放最后，它依赖前面造出来的数据。

### 7.2 在 Excel 里怎么填

1. 打开 `docs/测试用例-手工执行版.xlsx`，切到「测试用例」页。
2. 「实际结果」写你实际看到的内容，尤其是提示文案的原文——改文案时最容易发现不一致。
3. 「结论」从下拉里选：通过 / 不通过 / 阻塞 / 未执行。
4. 不通过时，在「缺陷编号」填 D-xx，并到「缺陷记录」页补齐复现步骤、期望、实际、严重级别。
5. 填完「结论」列，「执行汇总」页会自动统计各模块的通过/不通过数量。

### 7.3 提缺陷的最低要求

| 要素 | 说明 | 反例 |
|---|---|---|

### 8.1 三个值得注意的规律

把 15 个缺陷放在一起看，有三条重复出现的模式，比单个缺陷更值得记住：

**① 「有列、能筛、但不在模板里」** — D-02、D-03、D-04 都是这个模式。字段在库里有列、界面能筛，但模板字段清单里没有对应项，于是录入路径永远填不进去，而且不会报错，只是数据一直为空。这类问题只能靠「录进去、再筛出来」的完整链路才发现。

**② 「改了内容不改状态」** — D-08。写入是正确的，但流程状态没跟着走，结果是任务卡在原地。凡是涉及审核流的改动，都要问一句「状态该不该变」。

**③ 「只在一个环境成立」** — D-07。接口测试全过，因为直连后端是好的；但页面走的是前端代理，代理漏了一条规则。前后端分离的系统，凡是有静态资源或第二种 URL 前缀，都要在「前端地址」上验一次。

| 问题 | 经过 | 教训 |

## 十、未覆盖范围与残余风险
