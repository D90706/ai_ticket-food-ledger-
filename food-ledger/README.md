================================================================

⚠ 先看这段，能省掉一次「怎么还是电商那一套」的困惑：

    旧工程 = ../ai_ticket/             ← 上一个选题的 AI 客服工单（电商售后模板）

    两者已拆成同级目录，互不共用代码；端口刻意错开，免得启动错了还不知道：

        食材采购台账      后端 8081   前端 5174
        旧 AI 客服工单    后端 8080   前端 5173

    如果你打开 5173 看到"电商售后工单"，那是旧工程，不是这里。
    本系统请用 http://localhost:5174/

    启动命令在本目录里执行：
        mvn spring-boot:run


一个**能用的采购台账**，外加我们对「录入」的一点想法。

两件事同时成立：
    1 它是真的台账：录入、查询、筛选、统计、导出、批次追溯、临期预警
    2 它带着我们的做法：AI 把一句话抽成台账草稿、按法定项目判定合规、
      缺什么就说什么、不合规不许入账、管理员可退回补录

最重要的一条设计：
    **AI 只生成「待入账」记录，绝不直接入账。**
    台账是给监管看的东西，一条模型幻觉进去就是合规事故。
    人必须在入账这一步按一次键。


----------------------------------------------------------------
【为什么字段一半是列、一半是 JSON】
----------------------------------------------------------------

《食品安全法》第五十三条把进货查验记录的项目写死了：

    名称、规格、数量、生产日期/批号、保质期、进货日期、
    供货者名称、地址、联系方式（+ 索证索票凭证）

法律固定 = schema 固定。所以这 12 项是**数据库列**，
因为台账必须能「按日期筛选、按供应商汇总金额、按批号追溯、导出 Excel」。

单位自己加的那些（产地、冷链温度、农残报告号）进 `extra_json`，
由台账模板声明，前端按模板渲染，SQL 不关心。

原则：**稳定的东西建列，变化的东西建 JSON。**


----------------------------------------------------------------
【三级合规判定】
----------------------------------------------------------------

    RED    缺法定项目     → 不能入账（不是警告，是拦住）
    YELLOW 法定齐、缺凭证/选填 → 可入账，检查前补齐
    GREEN  全齐

临期与过期**不算级别**，只算提示：
    过期是业务事实（该退货），缺字段是记录缺陷（该补资料）。
    混成一个分数，人就分不清该干什么。

判定由代码做（`ComplianceEvaluator`），不交给模型：
这是确定性规则，同一笔采购不能两次判出两个级别。

【几个刻意的取舍】
----------------------------------------------------------------

没有 DELETE，只有作废
    台账是给监管看的东西，删行等于抹掉痕迹。
    作废必须填原因——比删除诚实。

修改必须带 version
    两个人同时改一行时，宁可报 409「你看到的是 v0，当前是 v1」，
    也不要静默覆盖。这是最容易发生也最难发现的事故。

采购员只能改自己录的
    台账共享，但「谁写的谁负责」不能松——不然出了错没人说得清。

AI 追问有上限（2 次）
    必填项并不总是能拿到（散装蔬菜没有批号）。
    没有上限，这条记录会永远卡在追问里。超限转「确认」，
    让采购员看一眼缺什么就提交，缺口显式暴露，而不是静默失败。

抽取的忠实性靠原文子串校验
    basis 里的每一段必须是采购员原话的子串，否则丢弃。
    编造的依据比没有依据更危险——它看起来很有说服力。

【三种录入方式，用手填也行】
----------------------------------------------------------------

采购录入端（http://localhost:5174/）有三个页签：

    记一笔  跟 AI 说话，它抽成台账草稿（信息不全时会追问、再让你确认）
    手填    传统表单，按模板字段一项项填
    我的记录 自己录过的，含补录（被管理员退回时在这里改）

**手填不是应急方案，是一等公民。** AI 是加速器，不是唯一入口：
模型挂了、网断了、或者采购员就是想自己填，都必须能记账。
一个只有 AI 能录入的台账系统，在食堂里是不敢用的。

两条路走同一段后端代码（`LedgerValueMapper` + 同一段合规判定），
所以不会出现「AI 填的能入账、手填的不能」。

手填表单的字段、必填、可选值、提示文案全部来自模板接口
（GET /api/templates/default），前端不写死字段——
否则改模板就得改前端，「字段可自定义」就是假的。

【它到底有多准】
----------------------------------------------------------------

不能只说"能跑"。定量评测在 `docs/eval-report.md`，一句话结论：

    16 条自建口述用例上，字段抽取准确率 100%（82/82），
    有值召回率 100%，瞎填率 0%，依据编造率约 2%~4%，零降级。

但这组数字有明确局限（样本小、用例与 prompt 同源、单一模型），
报告里逐条写了。正确说法是"在这 16 条上 100%"，
不是"准确率 100%"。

复现：

    RUN_EVAL=1 mvn test -Dtest=ExtractionEvalTest

实测中还发现两件事，都记在报告里：
    第一版 81.3% 的"级别一致率"其实是我的指标定义错了，不是模型差
    唯一一条"未命中"是我的标注与模板约定打架——模型是对的

【两个容易踩的部署/契约细节】
----------------------------------------------------------------

1 附件要单独代理
   vite 只代理 /api 的话，<img src="/uploads/..."> 会被当成前端路由，
   返回 index.html 给图片标签——页面表现是「图片加载不出来」，
   可直连后端 8081 的同一个地址又是好的，很难查。
   已代理 /uploads；生产环境把 uploads 目录交给同一个静态服务即可。

2 业务错误是 HTTP 200 + body.code
   包括 401 未登录。所以判断权限是否生效要看 code，
   不能看「有没有抛异常」（写测试脚本时就这么误判过一次）。
   浏览器侧 401：整页跳到对应登录页（admin -> /admin/#/login，
   录入端 -> / reload 后渲染登录卡片），顺带把内存里的登录态清掉。

【已知缺口】
----------------------------------------------------------------

    统计在 Java 里聚合，没走 SQL：几千行没问题，上百万行要改
    附件是公开可读的（URL 带 UUID 猜不出，但没有鉴权）：正式环境应改签名 URL
    单一模板：多套台账（不同品类不同字段）还没做
    历史数据没有品类：老记录需在「未分类」里逐条补，或跑一次按品名的批量预填
    业务错误统一 HTTP 200 + body.code（含 401/403/409）：与 REST 惯例不一致，
    改造要同时调整前端与 62 条回归，建议单独一轮做
    评测只覆盖 16 条自建用例，见 docs/eval-report.md 的「局限」一节
